# `tests/conformance/` — the conformance harness's pytest face

Operator-facing documentation (what the harness proves, how to read a failure, the baseline mechanism, CI) lives in `tools/cc/docs/conformance-harness.md`. This README is for anyone running or extending the test suite itself.

## Running it

```bash
cd tools/cc
.venv/bin/python -m pytest tests/conformance/ -v                    # everything this machine can run
.venv/bin/python -m pytest tests/conformance/ -m "not machine" -v   # hermetic — portable to any machine, incl. CI
```

`-m "not machine"` is the invocation to reach for on a machine with no real ecosystem installed, or when you want a fast, fully deterministic run. It is also what `.github/workflows/conformance.yml` runs — see that workflow's own header comment for why it is used explicitly rather than relying on every test file's own skip discipline.

## The two worlds (`conftest.py`)

**World A — synthetic**, via the `FleetFactory` fixture builder:

```python
def test_something(tmp_path):
    fleet = FleetFactory(tmp_path)
    fleet.product("claude").tier("foundation", rank=40).contributes("agents", {"cw": "real org content"})
    fleet.product("claude").tier("personal", rank=10).contributes("agents", {"cw": ""})  # empty-shadow case
    fleet.pin("claude", "foundation", ref="v1.0.0", orphan=True)  # reproduces RC-3's orphan-tag defect
    handle = fleet.build()
```

Real `git init`/commit/tag tier repos under `tmp_path`, real `HOME`/`CC_MACHINE_ROOT`/`XDG_CONFIG_HOME` isolation via `handle.env` (apply with the `apply_fleet_env` fixture for in-process calls). Nothing outside `tmp_path` is ever read or written. Every check needs both a fixture where it passes and a fixture where it fails — a check that has never been proven to fail is not a check, and `test_harness_core.py` enforces this as a standing fitness function.

**World B — machine truth**, marked `@pytest.mark.machine`: reads the real manifest, real tier repos, and real project repos, strictly read-only. The module-autouse `_conformance_machine_readonly_tripwire` fixture (built on `core/conformance/fsguard.MachineReadOnlyGuard`) fingerprints every guarded path before and after each test and fails the whole run, naming the offending path, if anything changed — this fires regardless of whether the test itself passed. Use `machine_readonly_guard(extra_paths=[...])` inside a test to extend the guarded set to dynamic real paths (a specific tier repo, a specific project's dimension paths) beyond the fixed core set the fixture already covers.

A test never straddles both worlds.

## Layout

| Path | What it covers |
|---|---|
| `conftest.py` | `FleetFactory`, the machine-readonly tripwire, `git_clone_local` |
| `test_harness_core.py` | Types, registry, report envelope/exit-code rules, fsguard, cache |
| `test_layer1_tier.py` … `test_rc_regressions.py` | One file per layer (tier / stack / repo-dimensions / lock / round-trip / regression pins) |
| `test_dimensions_*.py` | The 13 rubric-dimension modules under `core/conformance/dimensions/` |
| `fixtures/tiers/`, `fixtures/reference-install/`, `fixtures/degraded/` | Named fixture assets — real content, not synthetic placeholders where the check's own logic depends on real bytes (e.g. the `sample-agent.md` fixture H-5 reads sub-paths out of) |
| `baselines/` | The committed known-bad baseline, its generator, and the tests that validate both — see below |

## `baselines/`

`2026-08-12-reviewed-current.json` freezes every stable `(check id, subject)` pair's verdict as measured by the ordinary full collector, generated by `generate_baseline.py` from a live run — never edited by hand. Its `change_review` classifies every delta from the prior baseline and proves every PASS→FAIL has an attributed review. `report.compare_to_baseline` uses it to compute exit code 3 ("something that passed before now fails") independent of the absolute pass rate. Full explanation, including why regenerating it is deliberately not a one-command operation, is in `tools/cc/docs/conformance-harness.md`'s "The baseline mechanism" section.

`test_baseline_file.py` is the hermetic test module that keeps the committed file honest: non-empty, well-formed, no duplicate `(id, subject)` keys, at least one FAIL for each of RC-1 through RC-5, meets `TEST-MATRIX.md` §8's expected-fail-today floor, and — the part worth knowing if you are debugging the regression mechanism itself — actually replays the baseline through `report.compute_exit_code` both unchanged and with a synthetic PASS→FAIL flip, so the exit-3 path is proven against the real committed file on every run, not just asserted in a design doc.

## Adding a check

1. Register it (`register_check(id=, layer=, severity=, scope=, summary=, remediation=, ...)`) in whichever module owns its layer.
2. Write the check body as a pure function of its inputs — never re-implement ecosystem state a `cc` module already computes; call it.
3. Write a World-A fixture test proving it passes, and one proving it fails.
4. If it has a live instance on this machine, add a `@pytest.mark.machine` test asserting today's actual, measured verdict — and if that verdict is a known-bad condition, register the fail with `expected_today=ExpectedToday.FAIL` so a future baseline regeneration and `TEST-MATRIX.md` stay honest about what "today" means.
5. Regenerate the baseline deliberately (see `docs/conformance-harness.md`) once the check exists and its real verdict has stabilized — do not add a check without ever capturing its baseline entry, and do not regenerate the baseline as a substitute for understanding why a check newly fails.
