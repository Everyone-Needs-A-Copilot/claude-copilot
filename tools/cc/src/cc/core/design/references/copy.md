# Product language and truthful decisions

Use the product's own domain terms and name actions by their observable result.
State the problem and recovery in error messages. Distinguish validation failure,
permission denial, missing data and unavailable service rather than using one
generic failure message. Keep destructive consequences clear when a decision
actually needs them; do not add confirmations for routine reversible actions.

Preserve factual copy unless changing it is in scope. Do not fabricate customers,
metrics, pricing, compliance, capabilities or testimonials to improve a layout.
Label illustrative content where it could be mistaken for real evidence.

Check labels, headings, help text, validation, empty/loading states, notifications
and accessible names as one interaction. Avoid technical implementation terms
unless they help the intended user decide or recover. Test actual localized
strings, plural forms, numbers, dates and right-to-left layout as applicable.

UX owns functional wording and interaction meaning; UI design owns its hierarchy
and presentation; documentation owns durable help and reference. Verify that a
first-time user can explain the next action and that a returning user can scan it
quickly. Do not replace necessary precision with a framework-wide brevity rule.
