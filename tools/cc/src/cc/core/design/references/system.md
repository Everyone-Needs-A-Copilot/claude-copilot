# Design authority and reusable systems

Distinguish product truth, established visual conventions, and the decision for
this surface. Resolve them from existing requirements, SOUL, design specifications,
tokens, components, approved captures and walkthroughs. Do not require new PRODUCT
or DESIGN files merely because a tool expects those names; reference existing
files or export a task specification to a stable local file with its WP identity.

Classify the change as refine, extend or redesign. Refinement preserves established
identity and behavior; extension adds a compatible surface; redesign replaces
only the visual/interaction scope the owner authorized. A missing design document
does not make an existing product greenfield. Keep actual user instructions and
binding product constraints above imported aesthetic preferences.

Trace type roles, spacing, color semantics, radius, elevation, motion and component
states to their implementation sources. Mark inferred values as observations until
the design owner adopts them. Record variant and theme applicability. A generated
summary is a derived index, not a second authority that outlives its source hash.

Extract reusable tokens or components when repetition and stable responsibility
justify them. Preserve platform affordances, behavior, semantics and public APIs;
verify one caller before migrating the next. Avoid universal layer counts or a
new abstraction for every visual difference. Hand implementation concrete token
references, allowed variants, states and a baseline against which QA can compare.
