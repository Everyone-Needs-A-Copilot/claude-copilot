# Work lifecycle

Apply to coding, research, design, operations and advice, including direct specialist invocation. Load once per task; revisit only changed sources. The coordinator owns continuity and disposition; specialists record relevant decisions; independent QA reviews required evidence; the human owner authorizes destructive actions. Small work uses a short entry in its existing record (or the response when no durable record is needed), not a new task, initiative, board or retrospective file.

## Start or resume

Resolve current task, source identity, owner authority, unfinished obligations and acceptance evidence before trusting a summary. Preserve cumulative failures, attempts, spend and frozen scope across pauses, task labels and handoffs. Search narrowly for relevant lessons in existing memory and maintained narratives; follow source pointers rather than loading all history. Record a lesson's applicability and the decision or check it changes. “No relevant lesson found” with search scope is valid; never invent applicability.

For substantial QA-required work, include an observable `WORK-LIFECYCLE` criterion (or equivalent) and its evidence sources **before** freezing acceptance: applicable learning or justified no-match, current checkpoint, artifact disposition and verified holds. Define which retirement results are required for this task. Existing source-bound `tc` QA remains the acceptance gate. Do not retrofit a frozen contract silently, reset budgets or replace original acceptance authority; record omissions and route scope changes to the coordinator/owner. Missing required evidence fails the relevant criterion.

## During work

Update the existing task/work product and one maintained narrative for the body of work. Record consequential decisions, rejected approaches, measured failure mechanisms and corrections with original evidence references. Give temporary artifacts a purpose, owner, consumer and retirement condition when created. Preserve required software, LLM stub data, test fixtures, unique developer work, original QA, approvals and cumulative execution history. Summaries never replace those authorities.

A reusable lesson states: **when applicable → what failed → changed decision/check → source evidence → boundary or counterexample**. Keep project-specific rules in that project. Promote only supported lessons; distinguish explicit owner instructions from inferred advice. Memory is a selective locator to the canonical record, not another transcript: add a pointer only when future retrieval needs it, and avoid duplicate prose or routine end-of-session entries.

## Pause or handoff

In the existing task record preserve tested identity, approvals, failed criteria, charged usage, pending work, artifact locations and the next concrete action with owner. Preserve authoritative journey/run capsules where present. Distinguish awaiting a result, idle, stale evidence, blocked and complete. A live process is not progress; pausing does not imply acceptance. The outgoing coordinator owns a usable handoff; the incoming coordinator reconciles it against current files and task state.

## Finish and optimize

Consolidate a completed body into one maintained README or established equivalent: outcome, decisions, failures/corrections, lessons with boundaries and unfinished obligations. Supporting documents exist only for current need; no empty phase/decision/retrospective scaffolding. Keep legitimate software, design deliverables and evidence separate.

For accumulated clutter, run `/optimize` or the optimize skill using this sequence:

1. Measure current scoped files/directories/bytes and reading path; check branch, dirty state, unique commits, task authority, active processes/consumers, links and evidence dependencies. Age alone proves nothing.
2. Distill useful knowledge into the existing narrative and reconcile contradictions explicitly. Review preservation fidelity before proposing removal.
3. Classify each candidate: required active asset; necessary inactive original; redundant narrative; reproducible artifact; or unresolved hold. Archive only necessary inactive originals when useful: one private collection package plus a concise catalog, embedded membership/checksums and tested restoration. Keep active fixtures usable. An archive in the same project is not an independent backup.
4. Prepare exact affected paths, verified Git/archive recovery or demonstrated regeneration, dependency checks and rollback. Obtain exact human destructive approval **before** deletion, destructive overwrites or moves that discard/replace unique work, or destructive task/memory archival. Routine authorized editing and consolidation need no new approval. Summary quality and broad cleanup intent do not grant approval. Database archival must preserve execution history; uncertainty is a hold.
5. Execute only approved paths, recheck drift/consumers first, verify retained dependencies and recovery, and remove approved loose duplicates after archive verification. Report actual gross and net file/directory/byte reduction, including new archives and this process's evidence. Inventory, backup, compression or a new summary alone is not completed cleanup.

Each hold names owner, reason and next action. Report product-delivery acceptance separately from cleanup completion; a verified, owned hold can satisfy disposition evidence only when the criterion permits, without satisfying a required removal outcome; retaining it requires no fresh approval. Do not mark an optimization task complete while its required cleanup remains undone.

## Later use and measurement

Use the existing task record to follow **recorded → applied → outcome measured → independently accepted**. On relevant later work, link lesson source to the changed decision/check and observed result; retain negative results and counterexamples, narrowing or retiring misleading guidance. Retrieval or a retrospective alone proves no product benefit.

Measure comparable work: correct fresh-reader answers and files/words consulted; changed decisions; recurrence/rework under unchanged quality criteria; independent QA/owner outcomes; net repository growth and recoverability. Record baseline, scope, method and limitations. These are empirical checks, not guaranteed improvements or a new dashboard.

## Compact record template

Use a section in the existing task/WP; omit inapplicable fields with a reason:

- Task/body, owner, checkpoint, source identity and authority:
- Lesson/source/boundary (or searched scope and no-match):
- Decision/check changed; result/evidence; learning state:
- Current outcome, failures/corrections, remaining obligations and next owner/action:
- Artifacts: purpose/consumers; retain/archive/remove/hold; recovery and exact approval:
- Before/after gross and net counts/bytes; reading path; verification and limitations:
- Product acceptance / cleanup status (separate):

This is an instruction and evidence-review contract using existing task gates, not a network sandbox, daemon, automatic lesson validator or universal deletion enforcer. No provider calls are needed to perform a checkpoint.
