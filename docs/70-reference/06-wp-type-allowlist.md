# Work Product Type Allowlist

`tc wp store --type` is validated against `WP_VALID_TYPES` in `tools/tc/src/tc/services/wp.py`. An unrecognised type is rejected with a non-zero exit (`EXIT_VALIDATION`) and a message naming the offending value, every valid type, and how to add a legitimate missing one. This document records where the allowlist came from, so future additions are made the same evidence-based way rather than by guessing.

## Why this exists

Before this validation existed, `tc wp store --type` silently accepted any string. Agents probing the CLI for correct flag syntax created junk work-product rows with literal probe values (`INVALID`, `badtype`, `bogus`, `ZZZ`) in at least three independent projects (research-copilot, convoco, copilot-control-tower). Because this tool is shared machine-wide, a validation fix had to avoid the opposite failure mode — an incomplete allowlist silently breaking legitimate work-product storage in every other project.

## How the set was derived

**First pass (commit `dedf5d4`).** The allowlist was the union of every distinct `type` value found across every `tasks.db` reachable on the machine at the time (roughly twenty projects under `/Volumes/Dev/Sites/COPILOT/` plus mirrored copies), minus the probe/typo artifacts above, plus every type explicitly named in the framework's own agent instructions (`architecture`, `implementation`, `test-plan`, `documentation`, `specification`, `infrastructure`, `security-review`, `deploy_report`) and in `docs/10-architecture/01-agents.md` / `docs/50-features/03-knowledge-sync.md` (`technical_design`).

**Gap found and closed (this revision).** That first pass drew from `tasks.db` contents and `.claude/agents/*.md` only — it never grepped the framework's own **feature docs** (`docs/50-features/**`) or **skills** (`SKILL.md`). `docs/50-features/04-goal-driven-agents.md:315` instructs every agent's BLOCKED recovery workflow to run `tc wp store --type other ...`, a literal value the first pass's sources never surfaced, so every agent going BLOCKED and following its own documented recovery step failed with `EXIT_VALIDATION` — machine-wide, since this tool is editable-installed. The fix re-ran the sweep exhaustively across every repo under `/Volumes/Dev/Sites/COPILOT/` plus `~/.claude/`: documentation, agent definitions (framework and project-specific), skills, slash commands, orchestration templates, hooks, READMEs, and CLAUDE.md/CLAUDE_REFERENCE.md, explicitly including `docs/**` and `SKILL.md` this time. That sweep found four literal, currently-live `--type` values missing from the allowlist:

| Value | Source | Notes |
|---|---|---|
| `other` | `docs/50-features/04-goal-driven-agents.md:315` (claude-copilot, canonical) | Every agent's documented BLOCKED recovery step. The original gap. |
| `artifact-review` | `small-business-copilot/.claude/agents/aqa.md:73` | A project-specific custom agent (`aqa`), not part of the base framework roster, but a real, current, non-archived agent definition — the same evidence bar (`an agent definition`) the "Extending the set" policy below already sets. |
| `validation-review` | `small-business-copilot/.claude/agents/red.md:55` | Same project, its `red` (red-team) agent. Same reasoning as `artifact-review`. |
| `discovery` | `tc wp store --type discovery` still present in several projects' un-updated copies of `kc.md`: `convoco` (and four of its `.claude/worktrees/agent-*` copies), `convoco-google-verification`, `convoco-policy-build`, `preflight-copilot`, `rfp-copilot` | The **current** framework's own `kc.md` (in this repo and in `~/.claude/agents/kc.md`) has already moved this line to `cc memory store --type discovery` — a different tool (Memory Copilot, not Task Copilot) with its own, separate type-validation domain that `WP_VALID_TYPES` does not gate. But the listed projects have not run `/update-project` since that migration, so their materialized `kc.md` copies still literally instruct `tc wp store --type discovery`, and would fail with `EXIT_VALIDATION` exactly like `other` did if their `kc` agent reached that step today. Added on the same "real evidence of intentional use, still live" basis as the other three, not because it is the current canonical instruction. |

A candidate that was found but **not** added: `docs/40-initiatives/01-enforcement-convergence/README.md` (claude-copilot-internal) proposes two future `tc wp store --type` values, `qa-verdict` and `escalation`. That document's own frontmatter states `status: proposed` and its Non-Goals section states "Implementing any backlog item" is explicitly out of scope; no code path or agent instruction currently emits either value. Per the "Extending the set" policy below, a proposal is not evidence of intentional *use* — add these only if and when that backlog item actually lands and an agent is instructed to emit them.

**Re-checked exclusions.** The wider sweep was also used to re-verify the four excluded probe words (`bogus`, `badtype`, `ZZZ`, `INVALID`). Every occurrence of all four across the whole sweep is prose *describing* them as probe artifacts (this document, the `WP_VALID_TYPES` comment, cleanup handoffs in `research-copilot/docs/40-initiatives/01-verbatim-matching/HANDOFF.md`) — none appears as a literal instructed `tc wp store --type <value>` anywhere on the machine. The exclusion holds.

Hyphen/underscore/synonym variants that appear as real, independent usage (for example both `test-plan` and `test_plan`, both `security-review` and `security_review`) are each listed as their own valid entry rather than one being silently coerced into the other — coercion was explicitly out of scope for this fix.

## Extending the set

Add a type only when there is real evidence of intentional use — a framework doc (including `docs/50-features/**` and other feature docs, not just architecture/reference docs), a skill (`SKILL.md`), an agent definition (framework or project-specific), or a genuine (non-probe) work product already stored somewhere. Do not add a type just because a single CLI invocation needs it; that is exactly the shortcut that caused the original defect. When searching for evidence, grep the whole instruction surface, not just agent definitions — feature docs are exactly the source the first pass of this allowlist missed. When adding, keep `WP_VALID_TYPES` sorted and update this document's provenance note if the justification isn't self-evident from the addition itself. `tools/tc/tests/test_wp_type_doc_conformance.py` statically enforces this for this repo's own docs and agent definitions: it fails if any literal `tc wp store --type <value>` this repo instructs is missing from `WP_VALID_TYPES`, which is the mechanical guard against this class of gap recurring here (it cannot see sibling repos, so an addition sourced from another project like `artifact-review` above still has to be made by hand, the same way this revision was).

If a rejection turns out to be a false positive for a legitimate type this document doesn't yet know about, the CLI's own error message names the file to edit and the doc to update — resolve it there, not by coercing or defaulting around the check.

## What this does not gate

Validation only applies to new writes via `store_wp`. Reading, listing, and searching existing work products always work regardless of their stored `type` — including rows whose type predates this allowlist or was written directly to the database outside `tc`. Nothing here touches `get_wp`, `list_wps`, or `search_wps`.

`cc memory store --type <value>` is a separate tool (Memory Copilot) with its own validation domain; this document and `WP_VALID_TYPES` govern `tc wp store` only. `discovery`'s dual role (see table above) is the concrete example of why that distinction matters.
