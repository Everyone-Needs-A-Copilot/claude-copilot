# ADR-001 (initiative 06-central-resolution): One release pointer, zero per-project sync

**Status:** Proposed (owner confirmed the governing done block 2026-11-06; becomes Accepted when @agent-doc lands it and the pilot checkpoint passes)

**Supersedes:** codex-copilot `docs/40-initiatives/02-repository-portable-copilot/decisions/ADR-001-embed-assets-and-derive-caches.md` (copy model, status Proposed); claude-copilot `docs/40-initiatives/04-component-sync/decisions/ADR-001-lock-manifest-as-propagation-index.md` and `ADR-002-auto-apply-and-hold-on-dirty.md` (lock manifest as propagation index; auto-apply). Hold-on-dirty survives only as a migration-tool rule. `docs/30-operations/21-cc-reconcile-single-project-scope-and-plan-expiry.md` becomes historical: its project-reconcile defects are moot once project recipes are retired (see Consequences).

### Context

Every project carries about 151 framework-owned files (43 Claude, 108 Codex) and two checksum locks (`copilot.lock.json`, 40-49 KB, and `.codex-copilot.json`, a second per-file lock in some repos). `cc reconcile verify` is ready only when every checksum matches the current framework, so any change to any of those files makes all 71 live projects stale and each needs its own reconcile (about 100 s scoped, about 14 minutes unscoped) and commit. On this machine the same content is already installed once at user level and is byte-identical; the copies exist because Codex ADR-001 optimised for clone-and-go on a machine without the CSE. The owner has now decided that the framework only needs to work on machines with the CSE installed (one documented one-time machine install), so the copies buy nothing and cost a fleet re-sync on every release.

Forces and evidence (scratchpad reports, 2026-11-06): (1) Claude Code loads user-level agents, commands, skills and hooks in every project; project agents shadow user agents on a name collision. (2) Codex loads `~/.codex/AGENTS.md`, `~/.codex/skills`, user-scope plugin enablements and plugin hooks in every project; it caches plugin content per version and needs `codex plugin marketplace upgrade` (or reinstall for local sources) to refresh. (3) Codex hook trust is keyed `plugin@marketplace:hooks.json:event:group:index` plus a hash of the hook definition, not the plugin version: pre_tool_use hash 228971f9 is identical under 0.15 and 0.16 caches and three marketplace names. Every existing hook definition is already a constant dispatcher to `$PLUGIN_ROOT/hooks/<script>`, so script changes do not re-prompt; a renamed marketplace or a changed definition does. (4) Codex per-project trust (`[projects."<path>"]` in `~/.codex/config.toml`) is unavoidable machine state. (5) The Codex coordinator guard is in codex-copilot v0.16.8 and already in `~/.copilot/materialized/codex/plugins/codex-copilot` (0.16.8, includes `hooks/coordinator-guard.sh`), and `codex-copilot@enac-materialized` already has trust entries for the five older hooks; only the enablement still points at the stale `codex-copilot@codex-copilot-project` (snapshot 8d1b0de, cache 0.16.0, no guard). (6) Knowledge reaches runtimes four ways with four freshness rules; native auto-fire uses 17 hand-made links into mutable working trees, bypassing signed pins; 261 knowledge skills exist. (7) Machine installs are inconsistent: cc/tc from an immutable snapshot, `copilot` CLI from a hand-copied drifted `base-cli`, `tc-limits` and `~/.codex/skills/cli-authoring` linked into retired worktrees (both broken today: `tc-limits` exits 127), Control Tower 0.6.7 installed against v0.6.11.

### Decision

1. **One pointer.** `~/.copilot/current` is a symlink to an immutable release directory `~/.copilot/releases/<release-id>/`. The release directory contains `release.json` (schema 1: release id, created, previous release id, and per component `{name, tier, version, ref, commit, source, path, signer}`) and one entry per component: `claude-copilot`, `codex-copilot`, `cli-copilot`, `product-creation-copilot`, `control-tower` (version record; the .app is installed, not linked), and the tier overlays `knowledge/{foundation,organization,department-accounting,personal}`, `claude/{organization,department-accounting,personal}`, `codex/{organization,department-accounting,personal}`, `cli/{organization,department-accounting,personal}`. Company tiers (foundation, organization, department) are immutable snapshots materialised from the signed tags pinned in `~/.config/copilot/copilot.layers.yml` (signature verified, reusing the signed-knowledge extraction and framework-snapshot installer). Personal-tier entries are symlinks to the live `main` checkouts (owner is sole author; no signing). A release history file `~/.copilot/release-history.jsonl` records every flip. Generated per-release artifacts live inside the release directory: `codex-marketplace/` (the single Codex marketplace), `links.json` (the link plan), `codex-AGENTS.block.md`.
2. **Runtimes resolve through the pointer, never through projects.** `~/.claude/agents/*`, `~/.claude/commands/*`, `~/.claude/skills/*` and `~/.codex/skills/*` are per-item symlinks into `~/.copilot/current/...`, generated from one link plan that covers every framework agent, command and skill and every skill in every knowledge tier (261 knowledge, 58 machine; nearest tier wins on a name clash, same order as `cc skill`). Links are owned by a receipt (`~/.copilot/links-receipt.json`); the generator removes only links it created and never touches owner-authored items. Because links target the stable `current` path, a flip changes both runtimes in every project with no relinking; the plan is regenerated only when the set of names changes. `~/.claude/CLAUDE.md` carries one import line `@~/.copilot/current/claude-copilot/templates/framework-rules.md` (owner text untouched). `~/.codex/AGENTS.md` keeps owner text plus one generated managed block (Codex cannot import files); the block is regenerated at release and the combined size is checked against the 32 KiB budget. `paths.claude_copilot_root`, `~/.local/bin/{cc,tc,tc-limits,copilot}` resolve through `~/.copilot/current/...` (stable shim paths, changing targets).
3. **Codex plugins: one marketplace, enabled once.** All Copilot Codex plugins (foundation `codex-copilot`, `codex-copilot-internal`, `codex-copilot-accounting`, personal) are served by the user marketplace named **`enac-materialized`**, source `~/.copilot/current/codex-marketplace`, enabled once at user scope. `codex-copilot@codex-copilot-project` and `codex-copilot@codex-copilot-local` enablements and their marketplaces are removed (config backed up first); stale trust entries for them are left in place until closeout. `hooks.json` definitions stay byte-identical across releases, so trust given once survives releases (done-block assumption 3).
4. **Thin-shim hooks gated by a project marker.** Claude framework hooks (five events) are registered once in `~/.claude/settings.json` pointing at `~/.copilot/current/claude-copilot/.claude/hooks/copilot-hook.sh <event>`. The shim exits 0 unless the project has `copilot.project.json` (walking up from `$CLAUDE_PROJECT_DIR`/cwd), exits 0 while the project still carries its own legacy registration (prevents double firing during migration), honours `.claude/copilot-hooks-disabled`, and fails closed only with `.claude/copilot-required`. Codex plugin hook scripts apply the same marker gate inside the script (definitions unchanged). The coordinator guards (Claude `~/.claude/hooks/coordinator-guard.sh`, Codex `hooks/coordinator-guard.sh`) are NOT marker-gated: the coordinator rule is a global owner rule for every session.
5. **Projects keep only class-(a) state:** memory entries, `tc` state, project sections of CLAUDE.md/AGENTS.md, `owner: project` agents/commands/skills/plugins/hooks, `copilot.project.json` (the marker; schema adds `runtimes: ["claude","codex"]` always, optional `activePacks`, optional tier opt-ins), `.claude/cc/config.json`, non-framework settings, owned scaffolds, and policy markers. Every project gets both runtimes; there is no Claude-only declaration. Pack skills declared in `activePacks` are derived, untracked, gitignored links into `~/.copilot/current/codex-copilot/packs/...`, regenerated by `cc project init`.
6. **Both checksum locks retired.** `copilot.lock.json` and `.codex-copilot.json` are deleted by migration; nothing reads them afterwards. `cc doctor` verifies the machine (pointer, links, cache version vs pointer, trust, hook registration) and the project marker, not file checksums.
7. **`cc project init` (<10 s, target 1-2 s).** One Python process: write the marker, append thin project sections to CLAUDE.md/AGENTS.md only if absent (never clobber a foreign repo's files), add the Codex `[projects."<path>"]` trust entry atomically (flock, temp+rename, skip if present), derive pack links, update `.gitignore`. No census, plan, apply, network or git subprocess fan-out; no `projects.roots` gate (the path is registered instead); a non-Git folder works or returns a clean JSON error, never a traceback. `/setup-project` and `/update-project` become thin wrappers (init; doctor). Control Tower workspace activation calls the same function (one writer).
8. **Release = flip.** `cc release publish` = build release dir (verify signatures, materialise, generate marketplace, link plan and AGENTS block) -> atomic flip (`rename` of a temp symlink over `current`) -> apply link plan -> `codex plugin marketplace upgrade enac-materialized` (or the verified local-source equivalent) -> `cc doctor --release` -> append history. Rollback: `cc release rollback [--to <id>]` flips back to the previous immutable release (or a named one), reruns the marketplace refresh (old versions remain cached) and doctor. Pruning is an explicit, receipt-scoped `cc release prune --keep 5` that lists exact paths and runs only with owner approval.
9. **Fix fragile and stale installs as part of the release:** `tc-limits` -> `current/claude-copilot/tools/tc/tc-limits`; `cli-authoring` from its canonical `claude-copilot-internal/skills/cli-authoring` via the organization tier; `copilot` CLI installed by a real cli-copilot installer whose launcher resolves `current/cli-copilot` plus tier overlays (no `base-cli` copy, no hand-edited launcher); Control Tower 0.6.11 installed and recorded; product-creation-copilot included as a component with its skills linked in both runtimes.

### Consequences

Easier: a release reaches every project and both runtimes in one flip with no project touched; `cc project init` replaces a 100 s-14 min reconcile; one trust set for Codex; native auto-fire and `cc skill get` share one precedence and one pin; rollback is instant because releases are immutable. Harder or given up: a fresh clone on a machine without the CSE gets no framework behaviour (owner-accepted); project instruction files must carry only project facts (framework text lives in the release); the machine install becomes a hard prerequisite and its documentation must be maintained; per-item link plans must be regenerated when names change; a one-time fleet migration of 71 repos is required. Project reconcile recipes, `copilot.lock.json` verification, the per-project Codex plugin copy, `scripts/copilot-gate.sh` distribution, `fitness-check.sh` distribution and claude-copilot's bundled `plugins/codex-copilot` (and its pin gate `scripts/check-codex-plugin-pin.py`) are retired after the fleet migration. Reconcile defects #1 (single-project census) and #6 (non-Git crash) from the 2026-11-06 ops brief are not fixed: the migration tool and `cc project init` do not use reconcile; init carries its own non-Git criterion.

Reversibility: high until fleet migration (project copies are untouched and inert); after migration, git history in each project restores copies; the pointer itself rolls back instantly.

### Failure modes and degradation

- `current` missing or dangling: shims exit 0 with one stderr line naming `cc release status`; `cc doctor` fails loudly; `.claude/copilot-required` projects fail closed by design.
- Codex cache not refreshed after a flip: doctor compares cache version to `release.json` and fails; release command treats a failed upgrade as a failed release and offers rollback.
- Hook definition accidentally changed: CI fitness check compares `hooks.json` bytes to the previous release and fails the build unless the release notes declare a re-trust.
- Same-name skill precedence (Claude documents personal over project for skills): if verified, a project skill cannot shadow a tier skill; the link generator reports every collision between tier skills and project skills across the fleet before linking and leaves the user-level link out only where the owner marks the project override as intended.
- Skill-description budget: linking ~320 skills may exceed the runtime's skill listing budget; the generator reports total description characters per runtime and the spike measures truncation. Exceeding it is surfaced as an owner decision, not silently trimmed.
- Unmigrated projects during rollout: their Codex copies are inert once enablement moves to `enac-materialized`; their Claude copies shadow user agents (same bytes) until migrated; the Claude shim no-ops when a legacy registration exists, so hooks fire once.
- Signature verification fails for a tier: the release build fails; `current` is unchanged.
- Migration meets a modified framework file or ambiguous instruction-file section: hold, never delete; receipt lists the hold with owner and next action.

### Alternatives rejected

- **Keep the copy model, make reconcile fast** (fix census, memoise, batch cat-file): still one commit per project per release and two locks to police; does not meet "no per-project step".
- **Point runtimes at the live dev repos:** instant but ships unreleased edits to every project and bypasses signed tiers; owner chose release pointer for company tiers.
- **Directory-level links (`~/.claude/agents -> current/...`):** simpler, but would delete or hide owner-authored user-level items and cannot merge tiers; per-item links with a receipt preserve owner content.
- **Git submodules / out-of-repo project symlinks:** rejected for the same reasons as Codex ADR-001 (init friction, machine paths in Git) and unnecessary once resolution is user-level.
- **Keep `codex-copilot-project` as the single marketplace name:** reuses its trust entries but the same name is used by every project's repo marketplace (ambiguous precedence during migration) and it is sourced from a claude-copilot snapshot rather than the codex-copilot release. `enac-materialized` already serves the org plugins, already has 0.16.8 materialised and already holds trust for five of six hooks.
- **New `cc` reconcile mode that writes only thin state:** keeps the plan/apply/fingerprint machinery for work that is a few file writes; `cc project init` is simpler.

### Fitness functions (automated, land with the code)

1. `cc doctor --release`: `current` resolves to a release whose `release.json` validates; every link in the receipt resolves inside `current` or a personal checkout; no link targets a `.worktrees/` path; Codex cache version equals `release.json`; `codex-copilot@enac-materialized` is the only enabled Copilot Codex plugin source.
2. Release build check: `hooks.json` bytes unchanged from the previous release unless declared.
3. `cc project migrate --scan <roots>`: zero lock files and zero framework-copied files across live projects (the done-block scan).
4. `cc project init` timing test in the test suite asserts <10 s on a fresh and a foreign fixture repo.
5. Dependency direction: no runtime code path reads `copilot.lock.json` or `.codex-copilot.json` after retirement (grep-based test).

### Trade-offs

Optimised: propagation cost, consistency across runtimes and tiers, rollback speed. Sacrificed: clone-and-go portability to non-CSE machines; byte-level per-project reproducibility (replaced by machine-level release history). Reversible: pointer and links fully; fleet migration via git history.
