# Independent central-resolution audit — 7 November 2026

**Hold release readiness.** The candidate has two demonstrated migration defects: rollback can restore outside the project through a changed parent symlink, and migration can classify never-released branch content for deletion. The existing standalone Control Tower publisher also accepts source that fails the stricter hosted release authority contract. A fourth defect leaves the Codex trust check's timeout ineffective while its child is silent. No implementation, acceptance assertion, commit, live activation, publication or task closure was performed for this audit.

## Confirmed findings, ordered by severity

### F1 — High: migration rollback follows a changed parent symlink outside the project

- **Source:** `claude-copilot` commit `ee616244469678596c9f896b30fe517ed28abeb9`, `tools/cc/src/cc/core/project_migrate/rollback.py:16–22,51–59,109–125`. New migration implementation in the reviewed base-to-candidate range.
- **Trigger:** a valid backup records deleted `scripts/helper.sh`; before rollback, `project/scripts` becomes a symlink to another directory and the destination helper is absent.
- **Expected:** detect ancestor drift, preserve the external directory, report a conflict and leave restoration incomplete. **Actual:** rollback creates the helper outside the project, reports it restored with no conflicts, and changes the manifest status to `rolled-back`.
- **Impact:** recovery writes beyond its intended project boundary and reports successful recovery inaccurately. This reproducer establishes creation outside the project, not arbitrary overwrite of an existing different final file; existing final-file mismatch checks do hold such files.
- **Evidence:** `/private/tmp/cr-independent-compatibility-bgXZss/repro_rollback.py` and `rollback-result.json`. The unchanged candidate function ran under private HOME with the locked Python 3.14.7 runtime. The normal-directory control restored original bytes inside the project; the symlink variant returned `conflicts: []`, `outside_file_created: true`, and `final_status: rolled-back`. Security independently traced the same source path and confirmed the narrower creation claim.
- **Smallest correction:** validate project and backup containment and ancestor identity, reject symlink/absolute/traversal destinations, and perform restoration through directory descriptors/no-follow exclusive temporary creation so a post-validation swap cannot defeat the check. Do not mark the manifest rolled back while a boundary conflict remains.
- **Exact defect verification:** rerun those two private fixture cases against the corrected function: normal restoration must preserve original bytes/mode; changed ancestor must produce a conflict, create no outside file, and retain incomplete status. Add only direct traversal and ancestor-swap controls if the correction changes those paths. The predictable `.name.rollback` temporary is a related untested risk, not a separately demonstrated overwrite finding.

### F2 — High: unreleased branches become migration deletion authority

- **Source:** `claude-copilot` commit `ee616244469678596c9f896b30fe517ed28abeb9`, `tools/cc/src/cc/core/project_migrate/framework_index.py:95–111`, `:84–90`; `classify.py:38–51`; `planner.py:170–186`. The index implementation is new in this comparison range.
- **Trigger:** a framework repository has a capability file only on an unmerged, untagged experimental branch; a project has the same basename and bytes, with no explicit `owner: project` frontmatter. `add_git_history()` runs `git log --all` and indexes that branch.
- **Expected:** unreleased history alone cannot establish that the project file was distributed by the framework; preserve or hold it. **Actual:** `classify()` returns `("delete", <blob>)`. The planner translates this to DELETE with the reason “bytes identical to a file the framework released,” despite no release containing the fixture commit.
- **Impact:** ordinary local experimental branches can broaden the set of project files proposed for deletion. Execution still requires the migration's apply/approval path; this audit demonstrated erroneous classification and traced the planner, and did not delete any real project file.
- **Evidence:** `/private/tmp/cr-independent-compatibility-bgXZss/repro_history.py` and `history-result.json`: baseline main `de92399a9fcc9018c929e0a95430305e0a255828`; unmerged branch `148d521abbd53d5c3a3316741ae10e3456428c6c`; `git tag --contains` returned no tag; classifier returned delete for blob `3d49dd0f8291c06e3e9b75ce0e73a575fd57b96c`. Convergence owner independently inspected the fixture and source; the fixture's nonexistent-path control only checks the existence guard and does not establish released-file discrimination.
- **Smallest correction:** derive historical eligibility from verified release/deployment provenance or explicit lock receipts, not every reachable branch. Preserve basename/byte matching and explicit owner overrides, and hold files without sufficient provenance.
- **Exact defect verification:** use the same never-released branch fixture, requiring keep/hold instead of delete; direct controls must show a genuinely released matching file remains eligible and explicitly project-owned content remains preserved. No broader migration suite is authorized by this recommendation.

### F3 — High: standalone Control Tower source proof omits hosted authority requirements

- **Source:** `copilot-control-tower` commit `2573497788ecdc34f81c6c4b6999baeb41693c35`, `scripts/release-local.sh:99–115,125–131`; compare hosted `.github/scripts/verify-release-source.sh:21–23`. **Pre-existing:** the local source-proof block is identical at base `f45b3253e184909bc7ee99d4a147202ed1ff2ad9`; this is a release gap left open, not a newly introduced regression.
- **Trigger:** invoke `scripts/release-local.sh --tag v1.2.3 --verify-source-only` with an origin-advertised, annotated signed tag over an unsigned off-main commit and signer authority supplied through local Git configuration.
- **Expected:** under the release-authority contract, reject unless trusted fixed roots authorize the exact tag and signed commit and prove main ancestry before candidate execution or credentials. **Actual:** exit 0 and `release source verified`; independent `git verify-commit` and `git merge-base --is-ancestor <commit> main` both exit 1. Ambient `git verify-tag` replaces the hardened hosted verifier on this entrypoint. The local help promises signed-tag/origin equality only, whereas CT AGENTS invariant 4 and the intended publishing policy impose stronger authority requirements; this is an explicit policy/entrypoint mismatch, not a claim that its help promises main ancestry.
- **Impact:** documented direct-local publishing can proceed past source proof for content rejected by hosted policy. A trusted tag signature still authenticates the tagged bytes; this is missing fixed-authority, commit-signature and integration guarantees, not unsigned arbitrary content execution or a demonstrated hosted bypass. No credential stage or publication ran.
- **Evidence:** `/private/tmp/cr-security-audit-20261107/repro_ct.py`, `result.json`, and `unsigned-tag-control.json`. Candidate script SHA-256 `73f83ba23b01bf1a94a34358f0e5441b492d3e609d2b6ef463a36a933e1b6b68`; synthetic unsigned head `43fcc00d154ceda67c3b855e4a619b154eca67dc`; main `5b1869cb724344e4893f4a0dee41afcaccad48a3`. Private bare origin, HOME and synthetic SSH signer; unchanged script; cleanup `rm` stub retained evidence. Unsigned-tag direct control exited 1. - **Smallest correction:** reuse one caller-trusted fixed-authority preflight for local and hosted paths, requiring exact tag/commit, signed commit, allowed roots and fetched main ancestry before candidate execution. The candidate must not choose its own verifier or signer roots.
- **Exact defect verification:** rerun source-only off-main signed-tag/unsigned-commit rejection and unsigned-tag control; add the corresponding signed integrated exact-source success control against the shared corrected preflight, with private origins and no Apple/credential operations.

### F4 — Medium: Codex trust timeout cannot interrupt a silent child

- **Source:** `claude-copilot` commit `ee616244469678596c9f896b30fe517ed28abeb9`, `tools/cc/src/cc/core/release/codex/trust_gate.py:50–96`, specifically blocking `proc.stdout.readline()` at line 67 inside the deadline loop.
- **Trigger:** `app_server_hooks()` starts an app-server that keeps stdout open without sending a line. **Expected:** the requested timeout produces a timely `TrustGateError` and terminates the child. **Actual:** with `wait=0, timeout=.05`, the silent private stub delayed EOF approximately one second; the function returned the timeout error only after 0.9895 seconds. Responsive control returned an empty hook list in 0.1043 seconds.
- **Impact:** a hung child can stall release trust preflight indefinitely despite the nominal default 30-second timeout. The finite stub demonstrates timeout overrun; an indefinitely silent process was not left running. This is a liveness defect, not a demonstrated trust bypass.
- **Evidence:** `/private/tmp/cr-independent-compatibility-bgXZss/repro_timeout.py` and `timeout-result.json`, candidate module with private finite silent/responsive executable stubs and a three-second external watchdog. Security identified the source concern; compatibility reproduced it, and convergence independently read the blocking call.
- **Smallest correction:** use deadline-aware pipe readiness/nonblocking reads or bounded asynchronous communication; enforce one explicit deadline and reap the child on timeout.
- **Exact defect verification:** rerun the same silent and responsive stubs; silence must fail near the configured deadline (with a documented scheduling tolerance), and responsive protocol exchange must remain successful. Retain child cleanup checks.
