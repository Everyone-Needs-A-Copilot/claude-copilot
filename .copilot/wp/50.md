# TASK-40 Technical Design — Programmatic Code-Execution Path for tc & cc

**Status:** Proposed (design-only, awaiting user go/adjust). Depends on TASK-39 (FTS unification) for a stable shared data core.
**Tag:** [PERF] | **Overall complexity:** High (decomposed into Low/Medium increments below).

## 1. CURRENT-STATE FINDING (cited)

### tc — logic ENTANGLED in Typer handlers (the work is here)
- `tools/tc/src/tc/commands/task.py`: `task_create` (L34-73), `task_update` (L154-243), `task_claim` (L246-306), `task_next` (L309-355), `deps_add` (L363-405) embed raw SQL + validation + metadata-merge + agent-log writes directly in the command body. No domain function to call.
- `tools/tc/src/tc/commands/wp.py`: `wp_store` (L25-90+) embeds hybrid inline/file storage threshold logic inline.
- `tools/tc/src/tc/main.py`: `progress` (L61-139), `handoff` (L142-189), `log_cmd` (L193-237) inline SQL in the command body.
- `tools/tc/src/tc/db/` is connection + schema + TypedDicts ONLY: `connection.py` (get_db, init_db, find_db_path), `models.py` (TypedDict rows), `schema.py`. No domain operations.
- Verdict: tc has NO importable domain API. Composing N ops programmatically is impossible today without re-implementing SQL.

### cc — already has a clean importable API (mostly done)
- `tools/cc/src/cc/core/entry_store.py` exposes store_entry(), get_entry(), list_entries(), delete_entry(), search_entries_files() — all return plain dicts, side-effect-clean, no Typer/printing.
- `tools/cc/src/cc/commands/memory.py` (L15-32) imports those functions and is a thin wrapper — the desired end-state shape already exists for cc.
- Gap: `cc.core.memory_index` (FTS) is a separate path; public "search" is split between search_entries_files and search_index. A facade should pick the right one. skill_store needs a parallel facade.
- Verdict: cc is ~80% there at core/; it needs a published `cc.api` facade so agents import ONE documented surface, not internal core modules.

### Environment / code-execution availability (verified)
- `python3` (homebrew 3.14) imports BOTH tc and cc in one process: `python3 -c "import tc, cc; from cc.core.entry_store import store_entry"` succeeds.
- CAVEAT (real risk): tc installs to homebrew python (/opt/homebrew/bin/tc); cc to a dedicated venv (/Users/pabs/.local/bin/cc -> tools/cc/.venv). They co-import here only by luck of homebrew resolution — NOT portable. Do not require cross-tool single-process composition.
- Agents invoke tools via the Bash tool running CLI commands, one per call. There is NO MCP code-mode (legacy cc mcp_serve.py is dormant). The code-execution path = Bash running `python3 -c '...'`/`python3 script`. Confirmed available.

Bottom line: cc is mostly ready (publish a facade); tc requires a real service-layer extraction. The token lever is real and unpulled because tc forces one-CLI-call-per-op, each round-tripping full JSON back into context.

## 2. PROPOSED API SURFACE

Principle (ADR-040): extract domain logic into a service layer the CLI calls, then publish a flat `api.py` facade as the single agent-facing import. CLI behavior unchanged (backward compatible).

### tc: new `tc/services/` + `tc/api.py`
```
tools/tc/src/tc/
  services/{__init__,tasks,prds,wp,streams,activity}.py
  api.py   # flat re-export: from tc.api import create_task, store_wp, ...
```
Service functions: accept plain Python args (not Typer Options); accept optional `conn` so a caller batches many ops in ONE transaction (default conn=None opens/closes its own — preserves current CLI per-call semantics); return plain dicts/lists-of-dicts (same shape as today's --json); NEVER print, NEVER sys.exit; raise typed exceptions (TaskNotFound, ValidationError, ConflictError) instead of error_exit. Commit/rollback via an explicit `transaction(conn)` contextmanager in db/connection.py.
CLI handlers become thin: parse Options -> call service -> catch typed exception -> error_exit/output_error_json -> output_json/print. Behavior identical.

### cc: publish `cc/api.py` over existing core
- memory_store/get/list -> thin re-export of entry_store funcs.
- memory_search -> facade selecting FTS (memory_index.search_index) when index exists, else search_entries_files. Single documented entry point so the file/index split is invisible.
- No core refactor; cc/commands/memory.py unchanged.

Guarantees: one documented import per tool (from tc.api / from cc.api); CLI users see zero change; internal core/services/db evolve freely behind the facade.

## 3. USAGE PATTERN FOR AGENTS (worked token-win example)

Agents run a SINGLE Bash call executing one python3 block composing many ops and printing only a compact summary. Intermediate row payloads never enter context.

### "create PRD + 18 tasks + wire dependencies"
TODAY (Bash, one CLI call each): 1 prd create + 18 task create + ~17 deps add = ~36 round-trips, ~36 JSON payloads (title/description/metadata/timestamps/status) re-entering context. Order: 36 calls x ~250-600 tokens ≈ 9,000-20,000 tokens of intermediate output plus 36 tool framings.

WITH code-execution (one Bash call):
```bash
python3 - << 'PY'
from tc.api import create_prd, create_task, add_dependency
prd = create_prd(title="Checkout v2", description="...")
specs = [ {"title":"Schema migration","priority":0,"agent":"me","description":"Unit/integration tests required"}, ]  # +17 more
ids = []
for s in specs:
    ids.append(create_task(prd=prd["id"], **s)["id"])
for prev, cur in zip(ids, ids[1:]):
    add_dependency(task_id=cur, depends_on=prev)
print(f"PRD-{prd['id']}: created {len(ids)} tasks {ids[0]}..{ids[-1]}, {len(ids)-1} deps wired")
PY
```
Returns to context: one line, ~25 tokens. Net: ~9,000-20,000 -> ~25 tokens (~99% reduction on intermediate output). The agent already HAS the 18 specs; it does not need 18 echoed rows back.

### When to use which (added to agent shared-behavior guidance)
- PREFER code-execution for any multi-step tc/cc op (>=3 ops, or any create-then-link / batch-update / store-many). Default for ta (PRD/task scaffolding) and me (bulk WP storage).
- KEEP single Bash CLI call for one-shot reads/writes (tc task get 40 --json; one tc wp store; one cc memory search). No benefit wrapping one op.
- Read back only IDs/summary needed next; fetch full content for THAT one op with a targeted call.

## 5. RISKS / TRADEOFFS
- R1 Import side effects: api/services modules do ZERO work at import (no DB open, no env read). Connection opens only on call. Fitness check: importing tc.api/cc.api must not touch FS.
- R2 Connection handling: batching N ops risks a write lock; WAL + busy_timeout=5000 already set (connection.py L43-46). One transaction() per batch, commit once; rollback whole batch on error. Tradeoff: batch failure is all-or-nothing — safer than today's partial-progress-across-N-CLI-calls.
- R3 Error propagation: services raise typed exceptions; the python block surfaces a clear final line (not a traceback flooding context). Pattern: wrap block body in try/except printing "ERROR: <msg>" + nonzero exit.
- R4 Testing: existing CLI tests (tools/tc/tests/test_*.py) stay green (proves backward compat). Add service-layer unit tests (fast, no Typer) + a couple batch-transaction integration tests. Tests get EASIER because logic is finally callable without invoking Typer.
- R5 Cross-env importability (the real gotcha): tc and cc in different installed envs; co-import works here by homebrew luck, not portable. Recommendation: scope each code-execution block to ONE tool (tc-only OR cc-only), OR document+verify (cc doctor / tc db check) that the invoking interpreter sees both. Do NOT make cross-tool single-process composition a hard requirement. Reinforces A (cc-only) and B (tc-only) being independently shippable.
- R6 Pattern misuse: wrapping single ops in python adds overhead with no benefit. Mitigate via the >=3-op threshold rule in agent guidance.

## ADR-040: Service-layer extraction + flat facade for programmatic tc/cc
Status: Proposed.
Context: Agents invoke tc/cc one CLI call per op via Bash; every intermediate JSON re-enters context. Multi-step flows (PRD + 18 tasks) waste ~9-20K tokens of echoed rows — contradicting the framework's anti-bloat purpose (P0 lever in docs/70-reference/03-competitive-landscape.md). tc has no importable domain API (logic entangled in Typer handlers); cc already does at core layer.
Decision: Extract tc domain logic into a services/ layer returning plain dicts and raising typed exceptions; publish flat tc/api.py and cc/api.py facades as the single agent-facing import. CLI becomes a thin wrapper; behavior unchanged. Agents PREFER one python3 code-execution block for >=3-op flows.
Consequences: Easier — multi-step ops cost ~1 line of returned context; logic unit-testable without Typer; transactions batchable. Harder — two surfaces kept in sync (mitigated: CLI calls the same services); batch failures all-or-nothing; cross-env single-process composition not portable (scope blocks to one tool).
Alternatives Rejected: MCP code-mode server (setup is deliberately CLI-migrated; reintroducing MCP adds process+protocol surface for no extra token benefit over python3 via Bash). Raw SQL in python (duplicates validation/threshold/log logic, bypasses schema invariants). A `tc batch` JSON-spec subcommand (still serializes results through stdout/context, invents a DSL; a real Python API is simpler). Big-bang full tc refactor (rejected for A/B/C increments so biggest lever ships first).
