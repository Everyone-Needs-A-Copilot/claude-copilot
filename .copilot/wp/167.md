## GAP 1 — Automated cross-version regression eval (the JUDGE-automation gap) — P0

### (a) Problem statement
- **Absent:** any harness that scores agent OUTPUT quality across model/framework version bumps. Confirmed: no `.claude/evals/`, no promptfoo/deepeval configs anywhere under `/Volumes/Dev/Sites/COPILOT/*`, no `cc eval`/`tc eval` subcommand, no CI model-output check (CI is only `codeql`/`no-hardcoded-paths`/`smoke-tests`/`time-estimate-check` + `cli-copilot/ci.yml`), and codex parity is structure-only (`test_mirror_parity.py:12-80` asserts roster + section headers, never output).
- **Partially exists (procedural, not scored):** the mandatory QA gate (`CLAUDE.md` Testing Gate — `ARTIFACT`/`VERDICT`/`adversarial-run`) validates a *single run* pass/fail; it does NOT detect *cross-version behavioral drift*. Different guarantee.

### (b) Solution architecture — ADOPT promptfoo, WRAP behind `cc eval`
**Build-vs-adopt decision: adopt promptfoo as the assertion/LLM-judge engine, wrapped in a thin native `cc eval` subcommand.** Justification grounded in existing precedent:
- Don't rebuild an LLM-judge engine (classic build-vs-buy maintenance trap). promptfoo is YAML-driven, local-results, git-friendly — matches the "plain-text source of truth, SQLite cache" aesthetic of `cc memory`.
- Wrap it so the user surface stays CLI-consistent (`cc memory`/`skill`/`docs`/`usage`/**`eval`**) and **local-first/offline-degrading**, exactly like `cc usage` wraps vendored `claude-monitor` and `cc docs` is local-first with optional network fetch. `cc eval` runs deterministic assertions always (offline); LLM-judge cases skip with a clear "judge-unavailable" status when no key/network — same availability-gating philosophy as `adversarial-pass.sh`.
- **Reject** deepeval (pulls a pytest-resident Python metric stack; don't run two engines) and **reject** a hand-rolled judge (reinvents promptfoo). Per-memory: user prefers CLIs over MCP and local-first — `cc eval` honors both while reusing a proven engine.
- Trade accepted: a Node/`npx` dependency in a Python-CLI stack — mitigated by making promptfoo an OPTIONAL dependency with graceful deterministic-only degradation.

**Golden/regression cases:** stored as `.claude/evals/<agent>/*.yaml` (in-repo, diffable, git-versioned). Each case = a real input + expected PROPERTIES (assertions), never verbatim output. Examples grounded in agent contracts:
- `qa`: emits an `ARTIFACT:` line; `VERDICT` in {APPROVED, REJECTED}; writes no implementation code.
- `ta`: produces an ADR with Context/Decision/Consequences/Alternatives; every tech choice names a rejected alternative; complexity rating present and NO time estimate.
- `me`: writes code (does not delegate); routes to `qa`.
- skill-firing: given prompt X, the trigger-rich `description` causes skill Y to fire (deterministic).
- Assertion tiers (from `03-measuring-it.md`): deterministic (free, first line) → LLM-judge (1 call/case, **judged by a different model family** to defeat self-preference bias) → human-rated (calibration only). Discipline: binary pass/fail, one criterion per judge call, CoT-before-verdict.

**Wiring into version-bump + CI:**
- Trigger on a bump of `VERSION.json.framework` or `components.agents.version`.
- CI: add `.github/workflows/eval-regression.yml` running `cc eval --changed-agents` on PRs touching `.claude/agents/**` or `VERSION.json`. Slots in beside existing branch-protection + CodeQL required checks. **Deterministic assertions run on every PR; LLM-judge cases run only when an API secret is present** (don't make every PR a paid call — matches "defer cost until pain").
- Results → `cc memory store --type reference` keyed by `agent + framework version + git SHA` → regression history with NO new database, queryable via `cc memory search`.
- Pass-rate threshold wired into the existing `.claude/quality-gates.json`.

### (c) Components to add/change
- `tools/cc/`: new `cc eval` command group (resolve cases, invoke promptfoo when present, parse JSON, route scores to `cc memory`); optional-dep detection + degrade path; `cc.api` facade entry.
- `.claude/evals/qa/*.yaml`: first golden set (~10 cases) on ONE agent (qa) to prove the pattern, then template.
- `.github/workflows/eval-regression.yml`: PR + version-bump gate.
- `.claude/quality-gates.json`: add eval pass-rate threshold + P0-case-regression block.
- `VERSION.json` bump flow / release script: call `cc eval` before tagging.

### (d) Acceptance criteria / fitness functions
- **FF1:** `cc eval --agent qa` returns pass/fail JSON; exits non-zero if pass-rate < threshold or any P0 case regresses.
- **FF2 (meta-test):** deliberately removing the `ARTIFACT` requirement from the qa agent makes `cc eval --agent qa` FAIL — proves the harness catches regressions.
- **FF3:** a PR bumping `components.agents.version` without a green eval is blocked in CI.
- **FF4:** run scores are retrievable via `cc memory search "eval qa"`.

### (e) Risks & trade-offs
- Node/promptfoo dependency in a Python stack → mitigate: optional, deterministic-only degrade.
- LLM-judge cost & flakiness → assert properties not verbatim; binary; judge-on-secret only; re-run judge on disagreement.
- Golden-set maintenance/rot → start at 10 cases/1 agent; later add `cc memory check`-style staleness flagging for cases.

## GAP 2 — Per-task cost-cap ENFORCEMENT (turn observe → enforce) — P1 (native-flag layer is P0-cheap)

### (a) Problem statement
- **Absent (enforcement):** nothing halts runaway spend. No `budget_usd`/`max_tool_calls`/`--max-budget` wired in `tools/` or `.claude/`. `--max-budget-usd` is a Claude Code native print-mode flag the research only RECOMMENDS — not wired into any `tc`/dispatch path.
- **Partially exists (observe-only):** `cc usage` (`tools/cc/src/cc/commands/usage.py:108-162`) is *"Show Claude session quota / rate-limit state"* (`:128`) — probes/reads cache, prints, no `exit`/cap/threshold. It is a readout, not a control.

### (b) Solution architecture — feed `cc usage` into a hook that can `exit 2`
The natural seam is a **hook in `.claude/hooks/`**, mirroring how force-delegate and the QA gate already live in the `pretool-check.sh` PreToolUse dispatcher (block = `exit 2`; state in `.claude/hooks/state/streak-<session>.json`). Two enforcement layers:
1. **Per-run hard cap (native, cheapest):** wire `--max-budget-usd` into every non-interactive dispatch — `tc` worker, `/orchestrate` stream workers, Discord dispatch. This is literal loop-termination-by-spend. Lowest effort, highest immediate safety.
2. **Per-task tracked budget (`tc`):** add `budget_usd`/`max_tool_calls`/`actual_cost_usd` to the task model (`.copilot/tasks.db`); the worker passes `budget_usd` through as `--max-budget-usd`; actual cost recorded back → cost-vs-budget variance queryable.
3. **In-session soft guard (`pretool-check.sh`):** a new budget-rule branch reads the task budget + accumulated cost (from the existing `cc usage` cache `~/.claude/session-usage.json`, or a per-task tally in `.claude/hooks/state/budget-<session>.json`, atomic writes like the streak file) → warns at ~80-85%, blocks (`exit 2`) at 100%. A `Stop`/`StopFailure` handler captures `billing_error`/`rate_limit` and notifies via the Discord flow instead of dying silently.
- This is deliberately "turn the observe readout into the enforcement input" — GAP 2 reuses `cc usage`, it does not replace it.

### (c) Components to add/change
- `tools/tc/`: schema migration (`budget_usd`, `max_tool_calls`, `actual_cost_usd`); `tc task create --budget-usd`; worker/orchestrate dispatch passes `--max-budget-usd`; `tc task update` records actual cost.
- `.claude/hooks/pretool-check.sh`: budget-rule branch (warn/block via `exit 2`); state file `.claude/hooks/state/budget-<session_id>.json`.
- `tools/cc/`: `cc usage --session-cost --json` consumable by the hook (it already has `--json`).
- Escape hatch: `COPILOT_BUDGET=off`, folded into the `COPILOT_SAFETY=off` convenience alias (parity with `COPILOT_FORCE_DELEGATE=off`/`COPILOT_CAREFUL=off`/`COPILOT_FREEZE=off`).
- Defaults (from research): hard cap ~3-5x median cost of that task type; alert at 80-85%.

### (d) Acceptance criteria / fitness functions
- **FF1:** a task with `budget_usd: 0.50` that exceeds it has its next tool call blocked (`exit 2`) with a clear message; a synthetic runaway loop terminates instead of burning budget.
- **FF2:** `COPILOT_BUDGET=off` disables the block (escape-hatch parity).
- **FF3:** actual cost recorded on the task, visible via `tc task get`.
- **FF4:** grep proves non-interactive `tc`/Discord dispatch always passes `--max-budget-usd`.

### (e) Risks & trade-offs
- Cost-attribution lag: `cc usage`'s probe/transcript estimate may trail real spend → the in-session guard is a SOFT ceiling; only `claude -p --max-budget-usd` is a HARD ceiling. Document honestly.
- False positives on legitimately expensive tasks → per-task-type defaults + generous multiplier + escape hatch.
- **Codex parity asymmetry:** codex-copilot has no runtime hooks (uses `scripts/copilot-gate.sh`); the hook-based in-session guard must be hand-ported there or rely on `--max-budget-usd`-only enforcement. Pablo decision below.

## GAP 3 — memory→knowledge CONSOLIDATION (the genuinely unbuilt edge) — P2

### (a) Problem statement
- **Unbuilt:** the specific `cc memory` → knowledge-vault promotion (episodic→semantic graduation). Confirmed: no `promote`/`consolidate`/`graduate` path referencing knowledge/vault in `tools/cc/src/cc`.
- **NOT forbidden (correction from WP-166):** the One-Direction Principle (`knowledge-vs-capability-boundary.md:42-48`) bars only **vault→closed-silo** sync; it explicitly endorses inbound flow (*"a source silo is something to drain,"* `:46`).
- **Partially exists (adjacent):** `knowledge-sync` already promotes release commits→vault, auto-committed (`docs/50-features/03-knowledge-sync.md:32-51`); `/reflect` consolidates WITHIN memory only (`reflect.md:1-18`). knowledge-sync's own roadmap lists work-product/decision capture into knowledge as *"Not implemented yet"* (`:302-359, 733-757`).

### (b) Solution architecture — `cc memory promote`, reusing knowledge-sync's vault-write path, triggered from `/reflect`
- New **`cc memory promote <uuid>`** subcommand (CLI-consistent with `cc memory store/search/get/list/check/export`). Renders a durable memory entry as a Vault-Hygiene-compliant note (`boundary:52-62`): plain markdown, YAML frontmatter (`source: cc-memory/<uuid>`, `promoted_at`, `tags`, provenance), wikilinks, `NN-slug.md` in the correct section folder.
- **Reuse, don't rebuild:** route the actual vault write + auto-commit through `knowledge-sync`'s `update-product-knowledge.sh`/commit machinery (adapted for a memory-entry note) — that write-into-`KNOWLEDGE_REPO`-and-commit path already exists and is tested.
- **Respects One-Direction:** flow is memory(open)→vault(open), one-way; no vault→memory and no vault→closed-silo backflow. Vault stays canonical; the memory entry is the drained source.

**Promotion criteria (what graduates):**
- Type ∈ {`decision`, `lesson`, `reference`} (exclude `context`/`person` — project-local/PII).
- Durable (survived `cc memory check` staleness; or recurs across sessions) AND cross-project-general (not "this repo's auth runs behind Cloudflare").
- **Human-gated — NEVER automatic.** Memory is "accreted, noisy" (`04:83`); auto-promotion would pollute canonical knowledge.

**Trigger (recommended primary): extend `/reflect` with a Step 6 "Promote durable lessons."** `/reflect` is already the human-in-the-loop session-review surface; it surfaces candidate entries and, on explicit approval, calls `cc memory promote`. Secondary: ad-hoc `cc memory promote <id> --section <folder> --dry-run`. NOT git-tag-triggered (that is knowledge-sync's commits domain).

**Dedup/review gate:** before writing, search the target vault section for near-duplicates → warn/offer merge. `--dry-run` previews the note (knowledge-sync already has `--dry-run` precedent). The write is a normal vault commit, reviewable via `git log`/PR before push.

### (c) Components to add/change
- `tools/cc/`: `cc memory promote` (+ `--list-candidates`, `--dry-run`, `--section`); reuse knowledge-sync write/commit helpers.
- `.claude/commands/reflect.md`: add Step 6 promotion-review.
- Vault note template with provenance frontmatter.

### (d) Acceptance criteria / fitness functions
- **FF1:** `cc memory promote <uuid>` creates a hygiene-compliant `NN-slug.md` in the right vault section with provenance, auto-committed to `KNOWLEDGE_REPO`.
- **FF2 (One-Direction fitness function):** static check proves NO code path writes vault→memory or vault→closed-silo (guards against becoming a sync engine).
- **FF3:** `/reflect` only promotes on explicit user approval (never auto).
- **FF4:** dedup warns when a near-duplicate vault note exists.

### (e) Risks & trade-offs
- Knowledge pollution (the field's central memory risk) → human gate + durability/cross-project criteria + dedup.
- Provenance drift (promoted note vs evolving memory) → accepted by design: vault canonical post-promotion, no sync.
- Scope creep into a sync engine → hard rule: one-way, human-triggered, no backflow; FF2 guards it.
