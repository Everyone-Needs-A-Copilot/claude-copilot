# TASK-39 Technical Design — Unify cc & tc FTS5 into a shared indexing core (ADR-039)

**Status:** Proposed (design-only; awaiting user go/adjust before @agent-me).
**Tag:** [PERF] | **Overall complexity:** High (decomposed into Low/Medium increments).
**Unblocks:** TASK-43 (embeddings) — a single FTS contract is the seam an embedding backend slots under once.
**Builds on:** WP-50 (SearchBackend seam, TASK-32) and the R5 two-env packaging caveat from TASK-40.

## 1. CURRENT-STATE COMPARISON (cited)

### cc — standalone FTS, file-sourced, manual rebuild + best-effort incremental
- tools/cc/src/cc/core/memory_index.py:
  - Schema L19-26: CREATE VIRTUAL TABLE memory_fts USING fts5(id, type, tags, content) — STANDALONE table storing its own copy of the indexed text (no content= external-content option). Default tokenizer (unicode61).
  - Source of truth = committed markdown files .claude/memory/entries/<uuid>.md. memory.db is a gitignored disposable cache.
  - Maintenance is HYBRID: rebuild() L135-166 does full DELETE FROM memory_fts + reinsert of every .md (O(all entries), via cc memory index --rebuild). PLUS best-effort single-row index() L102-121 (DELETE-then-INSERT by id) and remove() L123-133, called from cc memory store (commands/memory.py L90-94) and cc memory delete (L197-200) but ONLY if memory.db already exists, wrapped in bare except: pass.
  - Search L168-193: WHERE memory_fts MATCH ? with NO explicit ORDER BY rank — relies on FTS5 default order, returns full content, no snippet(). cc memory search (commands/memory.py L221-228) tries index then ALSO file-scans as a backstop.
  - SearchBackend Protocol L33-70 + FTS5Backend L77-218 already exist (TASK-32). THE SEAM IS ALREADY HERE on the cc side.

### tc — external-content FTS, DB-sourced, trigger-maintained
- tools/tc/src/tc/db/schema.py:
  - Schema L64-67: work_products_fts USING fts5(title, content, type, agent, content='work_products', content_rowid='id') — EXTERNAL-CONTENT FTS: stores no duplicate text, indexes the base work_products table by rowid. Default tokenizer.
  - Source of truth = SQLite work_products rows.
  - Maintenance = 3 TRIGGERS L69-84: wp_fts_insert (AFTER INSERT), wp_fts_delete (AFTER DELETE, uses the ('delete', ...) external-content idiom), wp_fts_update (delete+insert). Always in sync, incrementally, no rebuild step.
- tools/tc/src/tc/services/wp.py search_wps L272-316: JOIN work_products_fts ON wp.id = work_products_fts.rowid WHERE ... MATCH ? ORDER BY rank LIMIT ? with snippet(work_products_fts, 1, ...). EXPLICIT BM25 rank + snippet + limit (TASK-40 already extracted into service layer).

### KEY DIVERGENCES
| Axis | cc | tc |
|------|----|----|
| FTS table kind | standalone (own copy) | external-content (mirrors base table) |
| Source of truth | markdown FILES on disk | SQLite ROWS |
| Maintenance | manual full rebuild + best-effort single-row | TRIGGERS (always incremental) |
| Ranking | implicit (no ORDER BY rank) | explicit ORDER BY rank (BM25) |
| Snippet/limit | none (returns full content) | snippet() + LIMIT |
| Tokenizer | default unicode61 | default unicode61 (same) |
| DB | .claude/memory/memory.db (disposable) | .copilot/tasks.db (source of truth) |
| Seam | SearchBackend protocol present | none; SQL inline in service |
| Install env | ~/.local/bin/cc -> tools/cc/.venv | /opt/homebrew/bin/tc (homebrew python) |

The two are NOT copy-paste duplication — they are two LEGITIMATELY DIFFERENT applications of FTS5 (file-sourced standalone vs row-sourced external-content). What is genuinely shared is the FTS5 MECHANISM: virtual-table creation, MATCH query with BM25 rank + snippet, tokenizer config. What must stay separate is the DATA and its sync strategy (files vs rows).

## 2. THE CRUX — packaging across two installed envs
WP-50 R5 (verified: /opt/homebrew/bin/tc vs ~/.local/bin/cc are separate installs): co-import works locally only by homebrew luck, NOT portable. A single shared IMPORTABLE package would have to be installed into BOTH envs and version-locked — a publishing + release-coordination burden disproportionate to ~80 lines of FTS helper, coupling two deliberately independent CLIs.

**Decision (ADR-039): vendor a tiny stdlib-only canonical helper into BOTH tools — not a shared installable lib, and not a shared DB.**
- ~80-line fts5_core.py copied verbatim into tools/cc/src/cc/core/fts5_core.py AND tools/tc/src/tc/db/fts5_core.py. Canonical copy lives in cc; a byte-identity guard test in both suites catches drift in CI (a vendored-sync fitness function).
- Depends only on sqlite3 + pathlib, so it works in either env with zero install changes. No PyPI, no cross-env import.
- NOT a shared index DB. cc memory entries and tc work products stay in their own DBs (memory.db vs tasks.db). Merging them couples privacy/portability models (cc memory is committed and travels with the repo; tc tasks.db is a workspace artifact). Explicitly rejected.

### What fts5_core.py provides (the shared mechanism)
- create_fts(conn, table, columns, *, content_table=None, content_rowid=None, tokenizer="unicode61") — emits CREATE VIRTUAL TABLE for either standalone (cc) or external-content (tc) form.
- create_content_triggers(conn, table, fts_table, columns, rowid="id") — emits the insert/delete/update trigger trio for external-content form (tc).
- fts_match(conn, fts_table, query, *, select, join=None, limit=None, snippet_col=None) — one MATCH+ORDER BY rank query path with optional snippet() and LIMIT. Both tools route search through this so ranking/snippet/limit are identical.
- escape_fts_query(query) — shared MATCH-expression sanitizer (today neither sanitizes; tc raises DatabaseError on malformed, cc swallows it — unifying fixes both).

cc FTS5Backend is rewritten to DELEGATE to fts5_core (slots UNDER the SearchBackend seam — seam stays, implementation shared). tc search_wps + schema.py DDL call fts5_core builders. Both keep public APIs, CLIs, DBs, and source-of-truth models unchanged.

## 3. cc rebuild-vs-trigger recommendation (decisive)
**Keep cc file-sourced; do NOT convert cc to trigger-maintained.** The inventory's "prefer triggers" applies to tc-shaped (row-sourced) data and does NOT fit cc.
Reasoning: cc's source of truth is markdown FILES, not table rows. SQLite triggers fire on table DML — they cannot observe a file being created/edited/git-pulled out-of-band. A trigger model would force all file mutations through the DB, inverting cc's file-first/DB-disposable design and breaking the "edit a memory .md by hand / git pull, then search" workflow. Full rebuild must remain the correctness backstop.
What we DO improve on the cc side (the real win behind the inventory note — avoid O(all-entries) per change):
- Make the best-effort incremental path (index_entry/remove_from_index) FIRST-CLASS and reliable instead of except:pass, so steady-state store/delete is O(1) and full rebuild becomes the RECONCILE op, not the per-write op.
- cc memory store auto-creates the index on first write (today only updates if memory.db already exists — L90) so incremental engages without a manual bootstrap.
- Keep cc memory index --rebuild as the explicit reconcile/repair (e.g. after git pull); --status drives a "rebuild recommended" hint.
Net: cc and tc converge on the SAME query MECHANISM and ranking, each retaining the sync strategy correct for its source of truth. "Behave the same" = same ranking, snippet, tokenizer, escaping, search contract — NOT identical maintenance internals.

## 4. BACKWARD COMPATIBILITY GUARANTEES
- cc memory search / cc memory index / tc wp search CLI names, flags, output shapes UNCHANGED.
- Existing memory.db and tasks.db keep working: CREATE VIRTUAL TABLE IF NOT EXISTS unchanged; tc triggers IF NOT EXISTS. No schema_version bump (tc DDL byte-compatible; cc has no schema versioning).
- If cc's standalone schema is touched, a one-time transparent rebuild on next --status/search reconciles — no user action, no data loss (files are source of truth).
- cc search RESULTS may reorder (adding explicit ORDER BY rank corrects BM25 ordering) but not membership — covered by a test asserting same id-set returned. tc results byte-identical (already used rank+snippet+limit).
- SearchBackend protocol preserved so TASK-43 embedding backend still drops in unchanged.

## 5. RISKS / TRADEOFFS
- R1 Vendored-copy drift (main tradeoff of rejecting a shared lib): mitigated by a byte-identity guard test in BOTH suites (fitness function); canonical copy is cc's.
- R2 cc ordering change: explicit BM25 rank reorders cc results. Mitigated: test asserts id-set equality vs old behavior; documented as intended fix.
- R3 First-write index bootstrap: auto-creating index on cc memory store adds tiny first-call cost + memory.db appears earlier. Mitigated: still gitignored, rebuildable.
- R4 FTS query escaping: shared sanitizer changes malformed-query behavior (tc raised, cc swallowed). Mitigated: unify on sanitize-then-match; test adversarial queries (quote, star, AND, unbalanced quotes).
- R5 Two-env reality: vendoring sidesteps cross-env import entirely; cost is the drift guard. Cheaper than publishing+version-locking a lib into two envs.
- R6 External-content ('delete', ...) idiom is subtle; centralizing trigger generation reduces chance a future column add breaks the trigger trio — net risk reduction.

## ADR-039: Vendored canonical FTS5 core under the SearchBackend seam
**Status:** Proposed.
**Context:** Two independent FTS5 implementations (cc standalone/file-sourced/manual-rebuild vs tc external-content/row-sourced/trigger-maintained) share the FTS5 mechanism but diverge in ranking, snippet, escaping, maintenance. cc and tc are installed in SEPARATE Python envs (WP-50 R5), so a shared importable library is impractical without publishing + version-locking into both. Goal: one search contract an embedding backend (TASK-43) can later slot under once.
**Decision:** Extract the FTS5 mechanism (table/trigger DDL builders, MATCH+BM25+snippet query, escaping) into a ~80-line stdlib-only fts5_core.py and VENDOR it byte-identically into both tools (canonical copy in cc), guarded by a byte-identity fitness test. Both route search/DDL through it. Data + sync strategy stay separate: cc file-sourced (rebuild-reconcile + first-class incremental), tc row-sourced (triggers). NOT a shared index DB. cc SearchBackend seam preserved.
**Consequences:** Easier — single ranking/snippet/escaping contract; TASK-43 drops under one seam; fixes apply to both; cc gains correct BM25 ordering + reliable incremental indexing. Harder — two vendored copies kept in sync (guard test); cc ordering changes (set-equality preserved); first-write index bootstrap for cc.
**Alternatives Rejected:** (a) Single shared installable package — must be published + version-locked into two independent envs, couples two CLIs, disproportionate to ~80 LOC. (b) Single shared index DB merging memory + work products — couples cc committed/portable memory with tc workspace tasks.db; different lifecycles/privacy. (c) Convert cc to trigger-maintained — cc source of truth is files not rows; triggers cannot observe out-of-band file/git changes, so rebuild must remain the backstop. (d) Leave as-is — divergent ranking/escaping and O(all-entries)-per-write remain, and TASK-43 would integrate embeddings twice.
