# Technical Design: Port `sales` vertical → CLI-first stack

## 0. Architectural clarification (the two homes — RESOLVED)

The prior recon's "drop skills+commands into cli-copilot as-is" is WRONG. There are two
distinct artifact classes with two distinct homes:

| Artifact class | Source (in `/tmp/kwp/sales/`) | Correct home | Why |
|---|---|---|---|
| **MCP connector (the integration)** | `.mcp.json` HTTP server entry | `cli-copilot/copilot_cli/services/<name>/` (Python Typer) | cli-copilot is a Python Typer CLI, NOT a `.claude/` project. The connector is runtime code. |
| **Skill prose (`skills/*/SKILL.md`)** | `skills/<name>/SKILL.md` (+ QUICKREF/README sidecars) | A `.claude/skills/` surface (recommend `claude-copilot/.claude/skills/sales/`) | These are Claude Code model-readable artifacts; they never execute, they instruct the model. |
| **Slash-commands** | NONE separate — `skills/*` ARE the commands | n/a | Plugin has NO `commands/` dir. Each SKILL.md carries `argument-hint`/`$ARGUMENTS` frontmatter, i.e. the skill IS the slash-command. One home, not two. |

**Key correction vs recon:** there is no separate `commands/*.md` to place. The plugin ships
9 skills, three of which (`call-summary`, `forecast`, `pipeline-review`) double as slash-commands
via frontmatter. Treat them as skills; Claude Code surfaces them as commands automatically.

## 1. Connector reference scaffold — CHOSEN: **Fireflies** (`~~conversation intelligence`)

### Why Fireflies over Apollo/HubSpot/Close:
- **Simplest real auth:** single static **Bearer API key** (`https://api.fireflies.ai/graphql`),
  identical to the Notion exemplar (`Authorization: Bearer <key>`). Apollo also Bearer but has a
  larger, paginated people/org surface; HubSpot/Close/Slack are **OAuth HTTP MCP** (callbackPort,
  refresh) — heavier, matches the reddit OAuth precedent not the Notion one.
- **Highest skill leverage:** "transcript" is referenced by 5 of 9 skills (call-summary x9,
  call-prep, create-an-asset, competitive-intelligence, daily-briefing). One connector unblocks
  the most rewires → best reference vertical.
- **Bounded surface:** 2-3 read verbs cover the workflows (list transcripts, get transcript,
  optionally get-by-meeting). No writes in phase 1 → low blast radius.
- NOTE-TO-VERIFY (non-blocking): Fireflies is GraphQL, not REST. The `create_client` wrapper is
  REST-shaped (base_url + path); GraphQL = single POST to `/graphql` with a `query` body. This is
  a minor client.py deviation (one `_gql(query, vars)` helper), NOT a framework change.

### Concrete scaffold — `cli-copilot/copilot_cli/services/fireflies/`

**`client.py`** (mirror `notion/client.py` structure):
```
SERVICE = "fireflies"
class FirefliesClient:
    __init__: create_client(base_url="https://api.fireflies.ai",
        headers={"Authorization": f"Bearer {settings.fireflies_api_key}",
                 "Content-Type": "application/json"})
    _gql(self, query: str, variables: dict) -> dict   # POST /graphql, returns data
    list_transcripts(self, limit=25, mine=True) -> dict        # transcripts(limit:) { id title date }
    get_transcript(self, transcript_id: str) -> dict           # transcript(id:) { sentences{speaker text} summary{...} }
    health(self) -> dict                                       # cheap me{ name } query for print_health
```

**`commands.py`** (mirror notion: `app = typer.Typer(no_args_is_help=True)`, lazy `_client()`):
```
copilot fireflies list   [--limit N] [--mine/--all]      -> list_transcripts  -> print_json
copilot fireflies get    <transcript_id>                 -> get_transcript    -> print_json
copilot fireflies health                                 -> health            -> print_health
```
Use shared `print_json/print_error/print_health/CopilotError` exactly as notion does.

**`config/settings.py`** — add one field under a `# --- Fireflies ---` block:
```
fireflies_api_key: str = ""
```
(loaded from `.env` `FIREFLIES_API_KEY` by existing pydantic-settings autobind; no code change)

**`main.py`** registration — two lines, alphabetical with peers:
- import block (~line 60, after `document`): `from .services.fireflies.commands import app as fireflies_app`
- add_typer block (~line 80): `app.add_typer(fireflies_app, name="fireflies", help="Fireflies conversation intelligence")`

### Exact rewire pattern (degraded-mode PRESERVED)
Skills keep their "works standalone / supercharged when connected" structure. We swap the
"connected" branch from an implicit MCP-tool assumption to an explicit CLI invocation, and keep
the standalone (paste-it) branch untouched.

BEFORE (call-summary, ~line 146):
```
**Transcripts connected (e.g. Gong, Fireflies):**
- Pull the full transcript
```
AFTER:
```
**Transcripts connected (Fireflies via cli-copilot):**
- If the user gives a transcript/meeting id, run:
    `copilot fireflies get <transcript_id> --json`
  and parse the returned sentences. If `copilot` is unavailable or the command errors,
  fall back to the standalone branch below (ask the user to paste the transcript).
```
Rule: every rewired branch MUST keep an explicit "if CLI unavailable → standalone" fallback so
the skill stays usable for non-CLI users (degraded mode is a hard requirement, see Risk 3).

## 3. Markdown home — RECOMMEND: `claude-copilot/.claude/skills/sales/`

Options weighed:
- (A) `claude-copilot/.claude/skills/sales/<skill>/SKILL.md` — RECOMMENDED. This framework already
  owns a `.claude/skills/` tree (architecture/code/design/... dirs exist) and a discovery path
  (`cc skill search`). Adding a `sales/` namespace is idiomatic, version-controlled, and travels
  via the existing sync/distribution machinery.
- (B) cli-copilot — REJECTED: Python project, no `.claude/` surface, no skill runtime for prose.
- (C) user's downstream project `.claude/` — viable for private use but loses framework
  distribution + `cc skill search` indexing; defer as a per-project copy, not the source of truth.

Decision: source-of-truth in `claude-copilot/.claude/skills/sales/`; the 3 command-skills surface
as slash-commands automatically. Sidecars (QUICKREF.md/README.md for create-an-asset) travel with
their skill dir.

## 4. Risks & failure modes

| # | Risk | Severity | Mitigation |
|---|---|---|---|
| 1 | **Skill→CLI coupling** — rewired skills become non-portable to users without cli-copilot installed | HIGH (biggest) | MANDATORY fallback clause in every rewired branch ("if `copilot` errors → standalone"). Never delete the paste-it branch. Coupling is additive, never replacing. |
| 2 | Auth/token storage — `FIREFLIES_API_KEY` lands in `.env` (plaintext) | Medium | Reuse existing pydantic-settings `.env` precedent (same as notion_api_key). Document, don't invent new secret store. Out of scope to change. |
| 3 | Degraded-mode regression — a rewrite that assumes the CLI breaks standalone users | HIGH | Fitness function: every SKILL.md must retain a "no connectors? / standalone" branch (greppable assertion in CI). |
| 4 | API drift ownership — Fireflies GraphQL schema changes; Anthropic owns upstream skill prose, we own the connector | Medium | We own `services/fireflies/client.py` queries. Pin a thin query set; `health` smoke-tests schema. Track upstream `sales` plugin for skill-prose updates separately. |
| 5 | GraphQL-vs-REST wrapper mismatch | Low | One `_gql` helper in client.py; no shared-wrapper change. |

## 5. Phased plan (dependency-ordered, NO time estimates)

**Phase 1 — Fireflies connector + commands (Complexity: Medium)**
Depends on: nothing. Deliver `services/fireflies/{client.py,commands.py}`, settings field,
main.py registration, `copilot fireflies list|get|health`. Tests: **unit (mock httpx GraphQL
responses) AND integration (live `health` against a real key in a gated test)** required.
Exit: `copilot fireflies health` green; `get <id>` returns parsed transcript JSON.

**Phase 2 — Markdown vendoring + call-summary rewire (Complexity: Low-Medium)**
Depends on: Phase 1. Vendor all 9 skills into `.claude/skills/sales/`. Rewire ONLY the
call-summary Fireflies branch to `copilot fireflies get` with fallback. Tests: skill-lint
(frontmatter valid) + a degraded-mode grep assertion (standalone branch present). Exit:
call-summary works both connected and standalone; other 8 skills vendored untouched.

**Phase 3 — Remaining connectors, lazily (Complexity: High, per-connector parallelizable)**
Depends on: Phase 1 pattern proven. Add connectors on demand, each its own stream:
- Apollo / ZoomInfo / Clay (enrichment) — Bearer, REST-ish → easy, follows Fireflies.
- HubSpot / Close / Slack / Outreach — **OAuth HTTP** → follow `reddit/client.py` precedent
  (token fetch+cache), heavier. Rewire the corresponding skill branches as each lands.
- Similarweb, Notion(already exists!), Calendar/Gmail (blank URLs in .mcp.json — upstream TBD).
Note: cli-copilot ALREADY has `notion`, `crm`(nocodb), `conv`, `brevo` — map `~~knowledge base`
to existing `copilot notion`, and consider `~~CRM` → existing `copilot crm` rather than HubSpot MCP.

## ADR-001: cli-copilot is the connector home; .claude/skills is the prose home
**Status:** Proposed
**Context:** Recon conflated a Python Typer CLI with a Claude Code `.claude/` artifact surface.
**Decision:** MCP connectors → `cli-copilot/copilot_cli/services/<name>/` (Python). Skill prose →
`claude-copilot/.claude/skills/sales/` (markdown). Skills invoke connectors via `copilot <svc> <verb>`
shell calls, always with a standalone fallback.
**Consequences:** Easier — each half evolves in its native ecosystem; connectors get real tests.
Harder — skills gain a soft runtime dependency on cli-copilot (mitigated by mandatory fallback).
**Alternatives rejected:** "drop everything into cli-copilot" (no skill runtime in a Python CLI);
"keep pure MCP" (user's stack is CLI-first, no MCP host).
