# Technical Design: Skill System Migration — MANUAL Discovery → AUTO-FIRING Frontmatter

## 1. Current State (investigated, not assumed)

### 1.1 How skills work today
- **27 `SKILL.md` files** under `.claude/skills/<category>/<name>/SKILL.md`. 16 are code-bearing (have `scripts/*.py` L3 scripts); 11 are prose-only (L1+L2).
- Discovery is **MANUAL**: an agent runs `cc skill search "<topic>"`, reads the returned path, then loads it with a prose `@include <path>` directive.
- **`cc skill search` is NOT FTS5.** Implementation `tools/cc/src/cc/core/skill_store.py::search_skills` (lines 197-219) is a plain **case-insensitive substring match** over `name + description + tags`. There is no SQLite/FTS5 index for skills (unlike memory, which has a real FTS5 index). The docs claiming "FTS5 keyword search" for skills are FACTUALLY WRONG:
  - `docs/10-architecture/00-overview.md:115` — "Discover skills by keyword (FTS5)"
  - `docs/30-operations/06-skills-authoring-guide.md:66` — "Used by FTS5 keyword search"
- **`@include` has NO preprocessor.** Grep of `.claude/hooks/` and `tools/` shows no resolver. `@include` is a model-convention directive embedded in agent prose — the model reads it and chooses to load the file. It is NOT machine-expanded.

### 1.2 cc skill CLI surface (`tools/cc/src/cc/commands/skill.py`)
- `skill list` — table of all discovered skills (scope: project|machine|all)
- `skill search <query>` — substring match, returns name/desc/path
- `skill get <name>` — prints full SKILL.md (pipeable, used as `@include $(cc skill get X)`)
- `skill path <name>` — prints absolute path
- Discovery walks `.claude/skills/` (project) then `~/.claude/skills/` (machine), `os.walk(followlinks=True)`, dedupe by name, project wins.

### 1.4 Native Claude Code / knowledge-work-plugins shape (target reference)
Confirmed from installed native skill `~/.claude/skills/gdoc-from-md/SKILL.md`:
```yaml
---
name: gdoc-from-md
description: >-
  <trigger-rich multi-sentence description ending in "Use when the user
  wants to ..."> 
---
```
Only `name` + a **trigger-rich `description`**. Auto-firing works because Claude Code surfaces every discovered SKILL.md's `name`+`description` into the model's available-skills context at session start; the model fires the skill when a prompt matches the description. No `cc skill search`, no `@include`, no `when_to_use` list.

## 2. Target Model (precise)

### 2.1 How auto-firing actually works
- Native Claude Code (and plugins) auto-load skill **metadata** (name+description) for every skill in a discoverable location (`.claude/skills/`, plugin skills). The model decides to invoke based on `description` match against the prompt. The skill BODY is loaded only when fired (progressive disclosure) — same token-economy goal the framework already has.
- The trigger surface is the **`description` field** — it must contain the trigger phrases that today live in `when_to_use` + `trigger_keywords`.

### 2.2 Replace vs complement
- **Auto-firing REPLACES `cc skill search` for prose (L1/L2) skills** — the model surfaces them natively; the explicit search step is redundant.
- **Auto-firing does NOT replace the L3 script execution path.** Code-bearing skills still need their script RUN deterministically (`python .../scripts/x.py`). Auto-firing only surfaces the SKILL.md prose; the agent must still invoke `Bash` on the script. So for code-bearing skills, auto-firing handles DISCOVERY but the Invocation section + `allowed-tools` still drive EXECUTION.
- **Keep `cc skill search`/`list`/`get` as a FALLBACK + tooling layer**, not the primary path: (a) Subagents (framework `@agent-*`) may NOT inherit the main session's native skill auto-surfacing — needs verification; if they don't, agents still need an explicit discovery call. (b) `cc skill list` remains the inventory/debug tool. (c) Scripts and CI can still query.

## 3. Migration Scope — Change Classes

### Class A — Skill file frontmatter (27 files) — Complexity: MEDIUM
- Rewrite each `description` to be **trigger-rich** (fold `when_to_use` bullets + `trigger_keywords` into prose ending in "Use when..."). This is the load-bearing change for auto-firing.
- Decide fate of `when_to_use`, `tags`, `trigger_keywords`, `trigger_files`: keep as supplementary (cc search still reads them) OR remove for native purity. Recommendation: KEEP (harmless extra YAML; cc fallback uses them; native CC ignores unknown keys).
- Standardize on `name` (retire the never-used `skill_name` from docs).
- Risk: hand-rewriting 27 descriptions is the bulk of the work; quality of trigger phrasing determines fire accuracy.

### Class B — Skill discoverability location — Complexity: MEDIUM/HIGH
- Native auto-firing requires skills to be in a location Claude Code scans. Verify whether `.claude/skills/<category>/<name>/SKILL.md` (nested category dir) is natively scanned, or whether native CC expects `.claude/skills/<name>/SKILL.md` (flat). If nested is not scanned natively, EITHER flatten the tree OR rely on cc tooling for nested skills. THIS IS THE PIVOTAL UNKNOWN.
- Risk: framework uses category subdirs (`security/`, `code/`...); native may not recurse. Could require restructuring all 27 paths → breaks every `@include`/`cc skill path` reference.

### Class C — cc CLI code (`tools/cc/src/cc/`) — Complexity: LOW
- No removal required if cc is kept as fallback. Optional: fix the FALSE "FTS5" labeling in help text; optionally add real FTS5 skill index for parity (separate, optional enhancement — NOT required for migration).
- `skill.py` / `skill_store.py` stay functional as-is.

### Class D — CLAUDE.md (5 spots) — Complexity: LOW
- Lines 33, 43, 109, 111, 185: reframe Skills row from "discover via `cc skill search` then `@include`" to "auto-fire via trigger-rich `description`; `cc skill search` is fallback/inventory." Fix FTS5 mislabel.

### Class E — Agent preambles (~13 files) — Complexity: MEDIUM
- Files: `.claude/agents/{me,qa,ta,do,doc,sd,uxd,uids,uid,cw,cs,cpa,sec}.md` each have a numbered step `N. cc skill search "..." -- ...`.
- Change: remove/soften the explicit `cc skill search` step to "Relevant skills auto-fire from their description; invoke `cc skill search` only if a needed skill did not surface." Pending Class B verification of subagent auto-surfacing — if subagents DON'T auto-surface, KEEP the explicit search step for agents and only change main-session docs.

### Class F — Command + doc references (~12 doc files) — Complexity: LOW/MEDIUM
- `docs/10-architecture/00-overview.md` (lines 13,20,27,115), `01-agents.md`, `02-philosophy.md`, `00-overview.md`, learning-roadmap, goal-driven-agents, testing, quick-reference, customization, skills-authoring-guide (rewrite L1 section + fix `skill_name`→`name`, fix FTS5 claim), `.claude/commands/{setup-project,skills-approve}.md`.
- Mechanical doc edits; large surface but low risk.

## 4. What stays vs removed
- STAYS: all 27 SKILL.md (re-described), cc skill CLI (as fallback/inventory/CI), L3 scripts + Invocation sections + `allowed-tools`, project→machine resolution.
- REMOVED/SOFTENED: mandatory `cc skill search` step in main-session flow + docs; the false "FTS5" skill claims; stale `skill_name` doc field.
- CONDITIONAL: explicit search step in agent preambles — removed only if subagents inherit native auto-surfacing (Class B/decision D3).

## 5. Risks
1. **Subagent auto-surfacing unverified (HIGHEST).** If framework `@agent-*` subagents do NOT receive native skill metadata the way the main session does, removing `cc skill search` from agent preambles silently breaks skill usage for the entire build chain. Must verify before touching Class E.
2. **Nested category dirs may not be natively scanned (Class B).** Could force a flat restructure of all 27 skills, breaking every path reference.
3. **Code-bearing execution gap.** Auto-firing surfaces prose but does not RUN scripts. If migration messaging implies "auto = done," agents may skip the deterministic L3 script that is the whole point of 16 skills.
4. **Double-firing / noise.** 27 trigger-rich descriptions auto-surfaced may over-fire on tangential prompts, adding context the framework was designed to avoid.
5. **Backward-compat.** Existing `@include $(cc skill path X)` and `cc skill get X` call sites keep working only if cc CLI is retained.

## 6. Phased Ordering (dependency chain, no time estimates)
- **Phase 0 — Foundation/Verification (BLOCKING):** Empirically verify (a) whether subagents auto-surface skills, (b) whether nested `category/` dirs are natively scanned. Resolves Class B and D3. Nothing else proceeds until known.
- **Phase 1 — Frontmatter migration (Class A):** Rewrite all 27 descriptions to trigger-rich form; standardize `name`. Independent of CLI changes; depends only on Phase 0 location decision.
- **Phase 2 — Doc + CLAUDE.md truth pass (Class C-help, D, F):** Fix FTS5 mislabel, `skill_name`→`name`, reframe discovery narrative. Depends on Phase 0 outcome for the "replace vs fallback" wording.
- **Phase 3 — Agent preambles (Class E):** Soften/remove `cc skill search` step. GATED on Phase 0(a). 
- **Phase 4 — Optional CLI hardening (Class C-code):** Real FTS5 skill index / help-text cleanup. Independent, last, optional.

## 7. Complexity Verdict
**Overall: MEDIUM-HIGH.** Mechanically most edits are LOW (docs/CLAUDE.md) to MEDIUM (27 descriptions). The MEDIUM-HIGH driver is the two unverified platform behaviors (Phase 0): subagent auto-surfacing and nested-dir scanning. If both are favorable, overall drops to MEDIUM. If either is unfavorable, scope expands (agent-preamble retention or full skill-tree flatten) → HIGH.

## 8. Open Decisions (user must decide)
- **D1 (TOP):** Verify and decide — do framework subagents inherit native skill auto-surfacing? Determines whether `cc skill search` is removed from agent preambles or retained for the build chain. EVERYTHING gates on this.
- **D2:** Replace vs complement — is `cc skill search` deprecated outright, or explicitly retained as fallback/inventory/CI tool? (Recommendation: retain as fallback.)
- **D3:** Skill tree shape — keep nested `category/` dirs (relies on cc tooling if native doesn't recurse) or flatten to native-scannable layout (breaks all path refs, larger blast radius)?
- **D4:** Frontmatter purity — strip `when_to_use`/`tags`/`trigger_keywords`/`trigger_files` for native minimalism, or keep them as harmless cc-fallback signal? (Recommendation: keep.)
- **D5:** Fix the false "FTS5 skill search" docs now (truth pass) or build a real FTS5 skill index to make the docs true? (Recommendation: fix docs now; index is optional Phase 4.)
