# TASK-43 Technical Design — Opt-in semantic embeddings backend for cc memory (ADR-043)

**Status:** Proposed (design-only; user pre-approved implementation).
**Tag:** [PERF]/[FEAT] | **Overall complexity:** High (decomposed into Low/Medium increments).
**Builds on:** WP-65/66 (TASK-39 FTS5 unification — SearchBackend seam + fts5_core vendored, byte-identical in both tools, BM25 ranking first-class). WP-50 R5 (cc and tc are SEPARATE installed envs).
**Depends on:** TASK-32 (seam), TASK-39 (unified FTS core).

## 2. DEPENDENCY STRATEGY — DECISION (the crux)

**DECISION: default OFF (FTS5 stays the only path for normal users, zero new hard deps). When enabled, use option (a) a LOCAL optional lib (sentence-transformers), lazily imported ONLY when `memory.embedding_model != "none"`. Provider-pluggable API form is a documented extension point but NOT the default and NOT in initial scope.**

Reasoning / trade-offs:
- Quality optimized: zero-friction default (no install bloat, no network, no API key, offline) for the 95% who never enable it. Embeddings inherently need a model — accepted only as an explicit opt-in cost.
- Why local lib over API as default: cc memory is local, committed, often offline/private; an API default would leak memory content to a third party and add a hard network failure mode and key management. A local model keeps the privacy/portability model of cc memory intact. The API path is provider-configurable (future `memory.embedding_provider`) but ships disabled — documented, not built, to avoid speculative surface.
- Sacrificed: when enabled, first run downloads/caches a model (~tens-hundreds MB into paths.embedding_cache) and adds the sentence-transformers + torch dependency footprint. This cost lands ONLY on opt-in users via `pip install 'claude-cli[embeddings]'`.
- Reversible: yes — `cc config unset memory.embedding_model` (or set "none") reverts to byte-identical FTS5 with one command; vectors table is just ignored.

**Lazy import + graceful degradation (NEVER crash, NEVER add import-time cost):**
- A `backend_factory.resolve_backend()` reads `memory.embedding_model` via config.resolve_key. If "none" → return `FTS5Backend()` (today's behavior, no embedding code touched, no import of sentence-transformers).
- If a model name is set → attempt `import sentence_transformers` INSIDE the factory (lazy, never at module top-level). On ImportError (extra not installed) OR model-load failure → log a clear WARNING ("embeddings requested but <reason>; falling back to FTS5 keyword search") and return FTS5Backend. Search still works, just keyword not semantic.
- Fitness function: importing cc.core.memory_index or cc.core.embedding_backend must NOT import sentence-transformers (assert module not in sys.modules after import). Off-path stays dependency-free.

## 3. STORAGE + COMPUTE + RANKING

**Storage — vectors in memory.db (NOT a sidecar).** Add an `embeddings` table to the SAME memory.db (already gitignored, disposable, rebuildable). Schema: `embeddings(id TEXT PRIMARY KEY, model TEXT, dim INTEGER, vector BLOB, content_hash TEXT)`. vector = float32 numpy bytes; content_hash = sha256 of indexed body for staleness detection. Why same DB not sidecar: memory.db is already the disposable cache co-located with the FTS table; one file to delete/rebuild; consistent lifecycle. Why not store in the .md files: vectors are model-specific derived data, not source of truth — they belong in the disposable cache, exactly like FTS rows.

**Compute on store + rebuild:**
- EmbeddingBackend.index(): compute vector for the entry body, upsert into embeddings table AND also write the FTS row (embeddings backend WRAPS FTS5Backend — it is hybrid, see ranking). Stamp model + content_hash.
- EmbeddingBackend.rebuild(): rebuild FTS (delegates to FTS5Backend.rebuild) then recompute vectors for all entries. `cc memory index --rebuild` recomputes vectors. If the configured model name differs from stored `model` column → rebuild detects mismatch and recomputes (model change = full recompute).
- remove(): delete from embeddings + FTS.

**Ranking — HYBRID (FTS5 prefilter + vector rerank), keep it simple and correct:**
- search(): (1) run FTS5 MATCH via fts5_core to get a candidate set (BM25-ordered, cheap, already correct from TASK-39); (2) embed the query once; (3) compute cosine similarity between query vector and each candidate's stored vector; (4) re-rank candidates by cosine, returning the same dict shape (id/type/tags/content). If FTS prefilter returns nothing (query terms absent but semantically related), fall back to a bounded full-vector scan (cosine over all embeddings, capped) so semantic-only matches still surface. Cosine over a candidate set (tens of rows) is plain numpy — no vector-index dependency (no sqlite-vss/faiss) needed at cc memory's scale. `memory.default_threshold` (0.7) gates minimum cosine for the full-scan fallback path.
- Trade-off: hybrid keeps BM25's precision for keyword hits while adding semantic recall, and avoids a heavyweight ANN index. Sacrifices: pure-semantic ranking when FTS prefilter is too narrow (mitigated by the bounded full-scan fallback). Reversible/simple.

## 4. CONFIG SURFACE (no new plumbing — uses existing keys)

- Turn ON: `cc config set memory.embedding_model all-MiniLM-L6-v2` (or any sentence-transformers model id). Or env `CC_MEMORY_EMBEDDING_MODEL=...` for a session.
- Default OFF: `memory.embedding_model` defaults to "none" (config.py L39) → FTS5 only.
- Install the optional dep: `pip install 'claude-cli[embeddings]'` (new extra in pyproject). Without it, enabling the model degrades to FTS5 with a warning (never crash).
- `cc memory index --rebuild` recomputes vectors for the active model; `--status` reports embedding state (model, vectors count, vectors-in-sync-with-files) in addition to FTS counts.
- Turn OFF: `cc config set memory.embedding_model none` (or `cc config unset`).

## 5. BACKWARD COMPAT — default-off guarantee (byte-identical)

- With embeddings off (the default), the resolve_backend() factory returns `FTS5Backend()` and NO embedding code runs, NO embedding lib imports, NO embeddings table is created. Search/store/index/rebuild/status behavior is BYTE-IDENTICAL to today's WP-66 state. A parity test asserts off-path results == current FTS5 results on a fixed corpus.
- Existing memory.db keeps working: embeddings table is `CREATE TABLE IF NOT EXISTS`, added only on the enabled path; off-path never touches it. No schema_version bump for off users.
- CLI names/flags/output shapes unchanged. SearchBackend Protocol unchanged (embedding backend just implements it). cc memory search returns the same dict shape regardless of backend.
- Disabling after use: vectors table is orphaned-but-harmless; `cc memory index --rebuild` after disabling drops to pure FTS.

## 6. RISKS / TRADEOFFS
- R1 Dependency footprint (sentence-transformers pulls torch): isolated behind optional extra; off-path users never see it. Mitigated by lazy import + fitness test asserting no import on off-path.
- R2 Model download on first enable (network + disk into embedding_cache): one-time, opt-in, cached. Documented in the enable instructions.
- R3 Model change invalidates stored vectors: rebuild detects model-column mismatch and recomputes; content_hash detects stale entries.
- R4 Cross-env: embeddings are cc-only (tc has no semantic need); no cross-env import concern (WP-50 R5). Scope strictly to cc.
- R5 Crash-safety: any embedding failure (import, model load, encode error) degrades to FTS5 with a logged warning — search never fails. Fitness test simulates ImportError and asserts FTS5 fallback + warning.
- R6 Performance: encoding cost on store is per-entry and small; search encodes the query once + cosine over a small candidate set. Acceptable at cc memory's scale (hundreds–low-thousands of entries). No ANN index introduced (rejected as premature — design for current + 1 order of magnitude).

## ADR-043: Opt-in local-model embedding backend under the SearchBackend seam
**Status:** Proposed.
**Context:** cc memory search is FTS5 keyword/BM25 (WP-66). Semantic recall needs a model, which is inherently a dependency. The SearchBackend seam + config keys (memory.embedding_model="none", paths.embedding_cache) already exist; the backend is constructed without consulting config. Goal: add semantic search WITHOUT imposing any cost on users who don't enable it, and without changing default behavior by a single byte.
**Decision:** Default OFF (FTS5 only, zero new hard deps). When `memory.embedding_model` is set, an EmbeddingBackend (implementing the existing SearchBackend Protocol) wraps FTS5Backend, lazily imports a LOCAL sentence-transformers model (optional `[embeddings]` extra), stores float32 vectors in an `embeddings` table inside the disposable memory.db, and ranks via hybrid FTS5-prefilter + cosine rerank (bounded full-scan fallback, threshold-gated). Backend selection reads config at one new factory point. Any failure degrades to FTS5 with a warning. API-provider embeddings are a documented extension point, not built.
**Consequences:** Easier — semantic recall available as a one-command opt-in; off-path users unaffected (byte-identical, no new deps, no imports); reversible. Harder — opt-in users add the torch/sentence-transformers footprint + first-run model download; two ranking paths to test; vectors invalidated on model change (handled by rebuild + content_hash).
**Alternatives Rejected:** (a) Embedding API as default — leaks local/committed memory to a third party, hard network failure mode, key management; kept only as a documented future provider. (b) Make embeddings a hard dependency / on-by-default — imposes torch on every user, contradicts zero-friction default. (c) sqlite-vss/faiss ANN index — premature for cc memory's scale (hundreds–thousands of entries); numpy cosine over an FTS candidate set is sufficient (design for current + 1 order of magnitude). (d) Sidecar vectors file — duplicates the disposable-cache lifecycle memory.db already provides. (e) Store vectors in the committed .md files — vectors are model-specific derived data, not source of truth.
