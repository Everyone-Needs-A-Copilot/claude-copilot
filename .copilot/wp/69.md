# TASK-41 Technical Design — Extension system → native Claude Code plugin (ADR-041)

**Status:** Proposed (design-only; user pre-approved implementation).
**Tag:** [FEAT] | **Overall complexity:** High (decomposed into Low/Medium increments).
**Builds on:** WP-50 R5 (cc and tc are SEPARATE installed envs — pipx/homebrew, NOT bundleable as Python in a plugin). docs/40-extensions/00-extension-spec.md (2-tier knowledge-repo override resolution).
**Depends on:** TASK-26 (single version source), TASK-36 (skills rollout).

## 1. CURRENT STATE (cited, verified)

Current layout (direct-clone usage today):
- .claude/agents/ — 8 markdown agents (ta, me, qa, do, doc, sd, design, kc) + _archive/.
- .claude/skills/ — local skills (loaded via `@include .claude/skills/NAME/SKILL.md`).
- .claude/commands/ — 18 slash-command markdown files (protocol, continue, map, orchestrate, setup*, update*, etc.) + keyword-parser.ts.
- .claude/hooks/ — pretool-check.sh, session-start.sh, subagent-stop.sh, user-prompt-submit.sh, bin/, state/, security-rules.json.
- .claude/settings.json — wires hooks with ABSOLUTE paths (e.g. /Volumes/.../.claude/hooks/pretool-check.sh). **This absolute-path coupling is the key thing a plugin must replace with ${CLAUDE_PLUGIN_ROOT}.**
- tools/cc/ + tools/tc/ — separate Python packages, installed independently (cc → ~/.local/bin venv, tc → homebrew). NOT shippable inside a plugin.
- Override layer: knowledge-repo resolution (project $KNOWLEDGE_REPO_PATH → global ~/.claude/knowledge → base agent). [agent].override.md / .extension.md / .skills.json. Resolved by the cc CLI extension tools (extension_get/extension_list/manifest_status). **Native Claude Code plugins have NO per-agent override/replace mechanism — they only ADD agents/skills/commands.** This is the load-bearing constraint.

No .claude-plugin/ or marketplace.json exists yet (verified — nothing matching plugin/marketplace at repo root).

## 2. PLUGIN STRUCTURE (additive, NOT a rewrite)

**DECISION: Add a `.claude-plugin/` manifest + a thin `marketplace.json` that POINT AT the existing .claude/ assets in place. The plugin is a packaging/discovery wrapper over the current tree, not a relocation of it. Direct-clone users are byte-for-byte unaffected.**

```
claude-copilot/
├── .claude-plugin/
│   ├── plugin.json          # NEW: the plugin manifest
│   └── marketplace.json     # NEW: single-plugin marketplace for team auto-discovery
├── .claude/                 # UNCHANGED — agents/skills/commands/hooks/settings.json stay
│   ├── agents/ skills/ commands/ hooks/ settings.json
└── tools/{cc,tc}/           # UNCHANGED — still installed separately
```

`.claude-plugin/plugin.json` (the manifest) declares the bundled assets by pointing at the existing dirs:
- `name`, `version` (sourced from the single version source, TASK-26), `description`, `author`.
- `agents`: "../.claude/agents" (the 8 base agents).
- `skills`: "../.claude/skills".
- `commands`: "../.claude/commands".
- `hooks`: a hooks config equivalent to .claude/settings.json BUT using `${CLAUDE_PLUGIN_ROOT}` instead of absolute paths, so hooks resolve wherever the plugin is installed. (Direct-clone keeps using settings.json with absolute paths; plugin install uses the manifest's ${CLAUDE_PLUGIN_ROOT} form. Both reference the SAME hook scripts.)
- output styles: none currently; reserved.

`.claude-plugin/marketplace.json` lists this one plugin so a team can add the repo as a marketplace (`extraKnownMarketplaces`) and `/plugin install` it. Enables team auto-discovery, replacing bespoke install scripts for the .claude/ asset layer.

Coexistence rule (fitness function): plugin.json and marketplace.json must reference the existing .claude/ paths — a test asserts every agent/command/skill/hook referenced by the manifest exists in .claude/, so the two layouts never diverge (single source of assets, two discovery mechanisms).

## 3. THE TWO-ENV REALITY — what's bundled vs what still requires cc/tc install (HONEST install story)

WP-50 R5 verified: cc lives in its own venv (~/.local/bin), tc in homebrew. A Claude Code plugin is a markdown/JSON/script bundle — **it CANNOT ship a Python environment.** Therefore:

**The plugin BUNDLES (pure assets, no runtime):**
- agents, skills, commands (markdown), hooks (shell scripts). These have no Python install step; they work the moment the plugin is installed.

**The plugin DOES NOT bundle (still requires separate install):**
- the `cc` CLI (memory + skills + config + extension resolution) — install via `pipx install`/`bash tools/cc/install.sh`.
- the `tc` CLI (task copilot) — install via homebrew/pipx.
- The plugin's agents CALL `cc`/`tc` via Bash; if those binaries aren't on PATH, the agents degrade (memory/task features unavailable) but the agent markdown still loads.

**Honest install story (documented):**
1. `/plugin marketplace add <repo>` then `/plugin install claude-copilot` → gets agents/skills/commands/hooks (the prompt-layer framework).
2. `pipx install claude-cli` (cc) and install tc → enables memory, tasks, skills CLI, extension resolution.
3. A post-install/`cc doctor`/`tc db check` step verifies both binaries are reachable and prints exactly which features are degraded if not. The plugin manifest documents this two-step reality up front — no pretending the plugin is self-contained.

## 4. PRESERVING THE PER-AGENT OVERRIDE LAYER (the load-bearing constraint)

Native plugins ADD agents; they have NO mechanism to REPLACE a specific agent's methodology with a knowledge-repo override. So the framework's existing 2-tier resolution (project → global → base) MUST continue to run as a thin custom layer ON TOP of plugin distribution, unchanged:

- The plugin ships the BASE agents only (the generic, standalone-functional ones). It never ships company overrides.
- Override resolution stays exactly as today: at agent-invocation time the protocol/agent consults `cc` extension tools (extension_get) which read $KNOWLEDGE_REPO_PATH (project) → ~/.claude/knowledge (global) → fall back to the base agent the plugin provides. The override layer is a RUNTIME prompt-assembly step (the agent loads its base instructions, then cc supplies any override/extension/skills to merge), NOT a file-replacement Claude Code performs.
- Because override resolution lives in cc (not in Claude Code's plugin loader), installing the framework as a plugin changes NOTHING about overrides: the plugin provides the base, cc layers the override on top at invocation. State this explicitly in docs: "plugin = base agents (the floor); knowledge-repo + cc = the override layer (the ceiling). Plugins add a floor they cannot lower; cc raises the ceiling."
- Fitness function: a test invoking an agent with a knowledge-repo override present must show the override applied even when the base agent came from the plugin install path — proving the two layers compose.

## 5. BACKWARD COMPAT — direct-clone unaffected

- Existing users who cloned the repo keep using .claude/settings.json (absolute hook paths), `@include` skills, and the cc-based extension resolution. NONE of those files change.
- The plugin manifest is ADDITIVE: a new `.claude-plugin/` directory referencing the same assets. Removing/ignoring it leaves the clone working identically.
- No agent/skill/command/hook file is moved or rewritten. settings.json stays as the clone's hook wiring; the manifest's ${CLAUDE_PLUGIN_ROOT} hooks block is the plugin's parallel wiring of the SAME scripts.
- Version is sourced from the single version source (TASK-26) so plugin.json and the clone never report different versions.

## 6. RISKS / TRADEOFFS
- R1 Two discovery mechanisms for one asset tree (settings.json vs manifest) risk drift: mitigated by a fitness test asserting the manifest references only existing .claude/ assets and the hook script set matches.
- R2 Hook path portability: settings.json uses absolute paths (clone-only); the manifest MUST use ${CLAUDE_PLUGIN_ROOT}. Risk a hook works in clone but not plugin or vice-versa — covered by an install smoke test in both modes.
- R3 Two-env install confusion: users may install the plugin and expect memory/tasks to work without cc/tc. Mitigated by the honest install story + doctor check that names degraded features.
- R4 Override layer invisibility: teams may assume the plugin replaces agents (it can't). Mitigated by explicit floor/ceiling docs + the compose fitness test.
- R5 cc/tc cannot be plugin-bundled (WP-50 R5): accepted and documented; the plugin is the prompt-layer, the CLIs are the runtime layer. Not a defect — a packaging boundary.

## ADR-041: Additive plugin manifest over existing .claude/ tree; cc-based override layer preserved
**Status:** Proposed.
**Context:** The framework installs by direct clone (.claude/ tree + separately-installed cc/tc CLIs). Teams want native Claude Code plugin auto-discovery. But (a) plugins can't bundle the cc/tc Python envs (WP-50 R5), and (b) plugins can only ADD agents — they have no per-agent OVERRIDE mechanism, which the knowledge-repo 2-tier resolution provides and which must be preserved.
**Decision:** Add a `.claude-plugin/` (plugin.json + marketplace.json) that POINTS AT the existing .claude/ assets in place (additive, no relocation), wiring hooks via ${CLAUDE_PLUGIN_ROOT}. The plugin bundles only the prompt-layer assets (agents/skills/commands/hooks); cc/tc remain separate installs (documented honestly via a doctor check). The per-agent override layer stays in cc as a runtime prompt-assembly step (project→global→base) layered ON TOP of the plugin-provided base agents — floor (plugin) vs ceiling (cc/knowledge-repo).
**Consequences:** Easier — team auto-discovery/install of the prompt layer; one asset tree, no rewrite; direct-clone unaffected; override capability fully preserved. Harder — two discovery mechanisms over one tree (drift guard needed); two-step install story (plugin + cc/tc) must be communicated clearly; hook path portability tested in both modes.
**Alternatives Rejected:** (a) Relocate assets into a plugin-only layout — breaks direct-clone users and the @include paths; rejected for backward compat. (b) Bundle cc/tc inside the plugin — impossible (plugins ship no Python env); WP-50 R5. (c) Drop the override layer and rely on plugin agents alone — loses the knowledge-repo per-agent override, the framework's core extensibility; non-negotiable to keep. (d) Re-introduce an MCP server to host overrides — setup was deliberately migrated off MCP to the cc CLI; reintroducing MCP adds process surface for no gain (cc already resolves overrides).
